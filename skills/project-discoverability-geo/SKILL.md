# 项目可见性 / GEO（生成式引擎优化）

## When to Use

- 用户问「我们项目 0 star / 搜不到，怎么提高可见度」
- 项目上线后要做对外推广
- 写对外物料（README / llms.txt / 发布文章 / awesome-list PR）

把一个**自研**的开源项目（或文章、作品）从"搜不到"变成"AI 会引用"。
适用：用户问「我们项目 0 star / 搜不到，怎么提高可见度」；项目上线后要做对外推广；写对外物料（README/文章/awesome-list PR）。

**与 `open-source-ai-agent-fit-assessment` 方向相反**：那个是"评估别人的项目值不值得用"；这个是自己项目怎么被看见。

## 核心认知（先摆正，否则会在错的地方使劲）

0. **一句话定义**：SEO 抢的是搜索结果页的位置，**GEO 抢的是 AI 回答里的被引用率**。用户入口从「关键词」变成「自然语言提问」，答案形态从「链接列表」变成「AI 生成的一段话」——要优化的就是这段话里有没有你。

**GEO vs SEO 对照表**（对外讲清定位时直接复用）：

| 维度 | SEO | GEO |
|---|---|---|
| 优化对象 | 搜索引擎爬虫 + 排名算法 | 大模型（训练语料 + RAG 实时检索）|
| 用户入口 | 关键词搜索 | 自然语言问答 |
| 争夺的东西 | 结果页排名、前 3 位 | 回答中的提及、引用、链接 |
| 度量指标 | 排名、点击率、收录量 | 被提及率、链接给出率、引用准确性 |
| 内容打法 | 关键词密度、外链、TDK | 结构化事实、FAQ、llms.txt、可被直接引用的「答案块」|
| 时效性 | 索引更新快（天级）| 模型知识有截止期；RAG 能部分弥补，但不稳定 |
| 稳定性 | 排名相对稳定 | **同一问题换次问法/换个时间，回答可能不一样** |

两者相通处：本质都是「让机器找到你、理解你、推荐你」。最大区别在**答案形态**：SEO 时代用户自己点链接做判断，**GEO 时代 AI 替用户做了判断——它引用谁，用户就信谁**。

1. **主战场是"联网引用"，不是"模型记住"**。已发布模型有训练截止期，新项目指望被"记住"不现实。真正要打动的是**带检索的 AI**（Perplexity / ChatGPT Search / 豆包 / Kimi / DeepSeek 联网模式）——它们引用的是**网页**。所以要做的是**生产值得被引用的网页**。
2. **0 star 是硬伤，技巧补不上**。AI 引用权重看 stars/forks/**第三方提及**。GEO 是果不是因——先搞出"有人用"（哪怕第一个陌生人 issue），比任何技巧都管用。
3. **重名是最大敌人**。项目简称若是业内热门缩写（如 "ACP" 就有多义），**所有对外物料必须写死全称**（`<简写> (<全称>)` + 一句消歧）。README 里的"不混淆声明"是加分项。

## 诊断四查（照这个顺序查，先看有没有"病"）

1. **搜得到自己吗**：去 Web 搜索和站内搜项目名/主人名，看前排是不是**全是重名项目**；
2. **有没有 AI 最爱引用的三样格式**：
   - `llms.txt`（放仓库根，给 AI 爬虫的站点说明）
   - **FAQ**（问答式是引用率最高的格式）
   - **横向对比表**（"best X for Y"类问题靠对比表回答）
3. **站外提及数**：博客 / awesome-list / 知乎掘金 —— **=0 就等于没有品牌认知**；
4. **仓库 hygiene**：description 一句话、topics 齐全、有 Release notes、双语 README。

## 物料清单（按投入产出排序，P0 先做仓库内的）

**P0（仓库内、零成本、当天可做）**
- `llms.txt` 放仓库根；
- README 加 **FAQ 一节 + 横向对比表**（
  铁律：**只新增，原内容一字不动**——让 canary 能 `git diff` 核对"只有两处新增"）；
- 补 repo 的 **description / topics / website** 字段；
- 有 tag 没 Release → **补一段 release notes**（解决什么 / 实测结论 / 一句话定位）。

**P1（站外，每篇 1-2 小时）**
- **中文实战文章**（发知乎/掘金/公众号）——中文 AI 吃中文网页，这是中文 GEO 的主粮；作者的**实战故事 = AI 最爱的"事实密度"**；
- **英文 dev.to 一篇**（英文 AI 吃 GitHub + 英文博客 + awesome lists）；
- 提 **2-3 个 awesome-list PR**（找 Protocols / Multi-Agent Orchestration 分区；一句话 + 链接；被收录 = 第三方背书）。

**发文渠道矩阵**（个人项目按需取用，商业公司全铺）：
- **开发者/技术**：GitHub（README/wiki/discussions）、dev.to、知乎、掘金、博客园、思否、InfoQ、Stack Overflow、Reddit、Quora
- **视频**：YouTube、B 站 —— **AI 会读字幕 transcript**，简介里放链接和关键词一样有效
- **社交**：X、LinkedIn —— 短平快，适合金句/版本动态/实测数据
- **问答预埋**：知乎/Quora/Reddit 回答相关领域问题（真诚回答、文末自然提及，别硬广）—— AI 答同类问题时这些是高频引用源
- **聚合入口**：awesome-list、Product Hunt、Hacker News（Show HN）—— 一次露出的长尾极长

**内容形态（按"被引用率"从高到低）**：
1. **一句话定义** —— 抢"X 是什么"，放首屏/开头第一句；
2. **FAQ 问答体** —— AI 最爱，整段抄；
3. **对比评测**（"X vs 竞品"）—— 表格形态最佳，AI 答对比题时照单全收；
4. **How-to 教程** —— 步骤化，AI 答"怎么做"时引用；
5. **数据报告/基准测试** —— 具体数字最难被编造，最容易被准确引用；
6. **实战复盘/踩坑实录** —— 真实细节是引用护城河，AI 编不出来，只能引你。

**"灌水的度"（三条红线）**：
- **改写，别纯复制** —— 同一底稿每个平台至少改标题/开头/案例，适配调性（dev.to 偏工程、知乎偏讨论、公众号偏故事）。纯复制会被 AI 去重，**浪费一次被检索的机会**；
- **质量 > 数量** —— 每月 1–2 篇扎实的，顶得过一天 10 篇水文；训练语料奖励长期存在的高质量内容，不是频率；
- **别碰黑帽** —— 关键词堆砌、批量小号自问自答、买外链，AI 时代模型的"品味"只会更刁，代价更大。

**P2（习惯）**
- 每月更新 FAQ / llms.txt（版本号、数据变了就同步）；
- 每月跑一次基线复测（下条），看引用率变化；
- 继续攒"有人用"的证据（第一个 issue / fork / 别人写的文章）。

## 基线测试记录法（"体检表"，别只做一次）

设计一组**固定 prompt**，每月在多家 AI（豆包/DeepSeek/Kimi/ChatGPT/Perplexity，**开联网**）问一遍、截图存档。

**prompt 必须分层**（每层测不同能力，各 2–5 条，固定不改）：
- **L1 通用问题（不带品牌名）**："两台电脑上的 AI agent 怎么互相发消息？"——测**能不能被发现**。**最难、价值最高**；
- **L2 品牌问题（带品牌名）**："<全称> 是什么？""<owner>/<repo> 这个仓库做什么？"——测**被说对的概率**（含链接准确率）；
- **L3 对比问题**："<项目> 和 A2A 有什么区别？"——测**定位有没有被理解**（AI 答对比题最爱抄对比表，提前画好）；
- **L4 口碑问题**："<项目> 有什么缺点？有人用过吗？"——测**风评**（AI 在传你什么话、负面有没有被放大）。

**五个核心指标**（别只记"提没提"）：
1. **点名率**：回答里提到你的比例（基础可见度）；
2. **链接准确率**：给出的链接是对的比例（点名了但链错 = 白搭）；
3. **张冠李戴率**：被认成同名/同类东西的比例（有重名风险必测）；
4. **引用深度**：提一句 / 展开讲 / 给链接 —— 分级记；
5. **情感倾向**：正面 / 中性 / 负面（L4 专用）。

记录形式：平台 × prompt 矩阵，每格记"点名/链接/备注"（我们的是 5×5=25 格）。

**复测纪律**：
- **每月一次**，同一套 prompt 一字不改，平台**一个一个手动过**；
- 每次记录**模型版本和日期**（模型更新会悄悄改结果，不记版本看不出趋势）；
- 检索不稳定是常态：关键结论**换个问法再验证一次**；
- **只看趋势，不纠结单次波动 —— "GEO 是月线图，不是分时图"**。

**预期：第一次大概率全军覆没（我们实测 L1 = 0/15），那就是基线，不丢人。**
记录表建议 4 个 sheet：测试说明 / Prompt 包（逐字复制，保证每月问法一致）/ 记录表（**预填行数 + 「是/否/未测」下拉**，每月追加后改日期）/ 汇总表（点名率 / 引用率 / 混淆率自动统计）。
做「给外部顾问的物料」时，**基线表由顾问侧产出、我们只负责跑并回填** —— 分工清楚，也避免各写一套表。

**度量"优化有没有用"，全看基线四条线**：
- L1 通用问题点名率从 0 往上走 → **分发在起效**；
- "点名→给链接"转化率往上走 → **仓库内优化在起效**；
- 张冠李戴率往下走 → **消歧内容在起效**；
- L4 口碑出现负面 → **公关该干活了**。

## ⚠️ 任何对外物料改了，先把所有「指向它的内部引用」扫一遍

读数方（尤其是 AI）会顺着这些指针找内容 —— **指针错 = 比没有更差**（它找到的是别的东西，会直接引用错内容）。

**「改结构」是一类独立的改动**：把 README 从「§一/§二/§三」改成「第一步…第六步 + 一、常见问题」时，**章节号全部失效**，而下面这些地方不会跟着动：
- **`llms.txt`**（最要紧 —— 它是专门喂给 AI 的入口文件）
- **`README-EN.md`** 与中文版之间的互指
- **`ENVELOPE-FORMAT.md` / 部署手册 / CHANGELOG** 里写的「见 README §x」
- **共享目录里的快照副本**（如 `README-zh-latest.md`）—— **快照会变成过期的假权威**，对外交付前必须重导或明确「只看线上链接」

**判据（一条命令）**：改完结构后 `grep -n "§\|see \|README\.md" <各物料>` 逐个对照**新章节标题**，逐条确认指向对得上；
**验收锚点**：从 `llms.txt` 里那条引用出发，人工走一遍能不能到达正确内容。
**输出物要包含「这轮做完了什么」的诚实记录**：纯文档改动在 CHANGELOG / Release 正文里注明「docs-only, no protocol behavior change」，别让读者以为有功能变化（下次发版时也别为纯文档改动硬打版本号 —— 让 writer 判断 A（新版本）还是 B（更新现有 Release 正文））。

## 商业视角：GEO 是"AI 时代的品牌词占领"

对商业公司，GEO 的本质一句话：**当客户问 AI"选谁"时，AI 报不报你的名字。**

- **官网必备三件套**：`llms.txt`（给 AI 的纯文本入口）、清晰的产品定义页、`schema.org` 结构化数据；
- **评价站占领**：G2 / Capterra / TrustRadius 上的公司主页与用户评价 —— AI 回答"选型"问题时的重要信源，B 端不能空着；
- **新闻稿进媒体库**：被正规媒体报道一次 = 进训练语料的"高可信区"，引用权重完全不同；
- **持续监测**：把品牌词、核心产品词、"X vs 竞品"做成每月基线 prompt，风评变化第一时间知道，而不是等客户告诉你；
- **B 端内容**：官网博客 / **产品对比页（"X vs Y"—— AI 答选型题直接抄）** / 客户案例 / 白皮书与行业报告。

## "引用友好"的写作法（同样一件事，换写法引用率差很多）

- **金句前置**：好记好抄，AI 生成回答时顺手就用。
  （我们的例："每台机器一个邮局"、"SSH 是门铃，ACP 是信箱；门铃只递指针，正文永远走 ACP"）
- **数字具体化**：具体数字比形容词更容易被准确引用，也更难被 AI 编造。
  （例：v0.7.0、18 秒门铃响、提示词走文件省约 20 倍 token）
- **主动消歧**：文章开头就写"跟 Zed 的 Agent Client Protocol、OpenAI 的 Agentic Commerce Protocol 没关系，只是名字撞了" ——
  基线里真出现过张冠李戴（实测 1/25），**不写就会继续错**。
- **给 AI 台阶**：明确告诉读者"**把仓库链接交给你的 coding agent，让它照着 README 装**" ——
  这句话既是使用说明，**也是给 AI 的引用话术**。
- **诚实边界**：写清"0 star 的个人项目""别指望开箱即用""企业级需求请用 A2A"——
  **不是示弱**：AI 引用时不会翻车，读者也不会有落差，**长期看是信任资产**。

## 许可证与归属声明（开源项目必查项）

GEO 不只管“被搜到”，也管**“被引用时说得对”** —— 许可证/归属写错，AI 照抄的就是错话。

**开源项目自检四步**：
1. **`LICENSE` 是不是标准全文**（逐字对照官方模板；版权行写 `Copyright (c) <年份> <owner>`）；
2. **`NOTICE` 只在 Apache-2.0 等许可证下需要** —— **MIT 不要求 NOTICE**，别多此一举；
3. **依赖链的许可证兼容性**：MIT 项目可安全使用 Apache-2.0 / BSD / **MPL-2.0** 依赖。MPL 是**文件级弱 copyleft**，**以外部进程方式调用不触发传染**（但**仓库内不要 vendor 对方源码**，否则要随附许可证）；
4. **归属声明的写法要“闭合”**：写了“英文版归属见 X.md”就必须说清**中文版在本文哪一段**，否则读者/AI 会以为另有中文文件。
   · 错误示范：「本项目以 MIT 发布；**英文版**归属声明见 `ATTRIBUTION-EN.md`」
   · 正确：「本项目以 MIT 发布（见 `LICENSE`）；**归属声明：中文见本节上文，英文见 `ATTRIBUTION-EN.md`**」
   · 判据：把这句话单独拿出来读，**每个代词/指代能不能在同页找到落点**；找不到就是悬浮指针。

**改完许可证/归属文案后**：中英同步改（只改一处最易被漏），并 `grep -c "MIT\|ATTRIBUTION"` 对一遍两版是否表达同一件事。

## ★ README 的读者是 AI Agent，不是人（用户明确口径）

> 「既然这东西是给 agent 执行的（该装 OpenSSH 就装、该装 Syncthing 就装），就写成一安装手册就行，不用那么复杂；有些东西还是有点冗长。」

**目标形态：把链接丢给一个 agent，它照着一路装完即可**。因此：
- **结构**：① 一句话定位 + 不混淆声明 → ② **装（Agent 照做，命令可直接照拄）** → ③ 用（命令表）→ ④ **坑/FAQ** → ⑤ 原理/免责/归属（放最后，agent 不用读）。
- **写在最前的必须是可直接执行的命令**，不是解释。安装步骤给**平台分支**（Windows 的 `Add-WindowsCapability` / Linux 的 `apt`）。
- **FAQ 用真踩过的坑**，别用臆想的"常见问题"——一个真实坑（带错误串 + 为什么 + 修法）比十句泛泛而谈有价值。
- **删掉论证性/解释性的长段**——它们对 agent 无用，只增 token。判断标准：删了之后"能不能照做"？能，就删。
- **保留**（别删错）：架构图、项目故事/人名等有人情味的部分、**上游依赖的致谢与归属声明**（用了别人的东西必须写）、横向对比表。
- **多语言策略**：先定稿中文；**英文版等中文定稿后一次性翻译**，不要"一版一版同步"（浪费且易不一致）。

**修正过时表述**：项目能力变了，README 里的"做不到 X"要同步更新——**过时的诚实声明会自我贬低**（AI 引用时读到"做不到"会降低评价）。改法：从绝对否定改成"需额外通道（本项目不内置，但已实测可用 …）"。

## 实战基线（ACP-lite 项目真实数据，作参照系）

**2026-10-16 基线**（5 平台 × 5 prompt = 25 格）：
```
点名 9/25（36%） ｜ 给仓库链接 4/25（16%） ｜ 张冠李戴 1/25（4%）
L1–L3 通用问题：0/15（全军覆没）—— 不带品牌名问时，AI 完全不知道我们
L2 品牌问题（直接点名问）：9/10（90%）—— 一旦被点名，基本能说对
```
**三条结论**：描述能对、链接看运气；**通用问题完全不可见**；检索稳定性是最大短板。

**平台差异备忘（同一套题，结果不一样）**：Kimi 最好（点名+给对链接+消歧干净）；ChatGPT P5 满分但 P4 说没仓库；Perplexity 点名不给链接；**DeepSeek 自相矛盾**（P4 给了链接、P5 说找不到 —— 说明索引还不稳定）；豆包 P4 坦承查无资料、P5 靠 GitHub API 读准了。

**这个基线就是"优化有没有用"的参照系** —— 做完 P1 站外三件套后复测：

## 分工（多 agent 流水线场景）

如果环境里有多个 agent（**多个 AI 助手/编程助手**），GEO 任务天然可拆：
- **诊断方**（如 "绒毛"）：出诊断 + 物料草稿（"包"）；
- **物料的合入方**（如 Codex，writer）：照草稿改仓库、提交、push；
- **用户本人**：跑基线测试 + 写中文实战文章（他的实战故事 AI 最爱引）；
- **其他人**（其他 agent）：awesome-list PR + 每月复测，做成固定动作。

物料包经 ACP 共享目录传递；合入方按"合入说明"照做（**合入说明里写清：commit message、验收标准、能改/不能改的字段**）。

## Pitfalls

1. **合入时严格"只新增、不改原文"**——让验收方能用 `git diff` 行数核对。历史内容一字不动。
2. **改名/重命名要全局统一**：对外物料里项目名必须一致地写全称，**不同物料别用不同写法**，否则消歧白做。
3. **物料里的"社区影响力"类表述要与实测一致**（star/fork 为 0 时**别暗示"广受关注"**——会被 HR/审查一眼看穿）。
4. **push 可能卡在环境问题上，不是权限**：`git push` 报 `EXIT=128` / `git-remote-https.exe 应用程序错误`（空指针崩 0x0）→ 根因是 **Windows 的 `schannel` SSL 后端**在拉起 HTTPS 远程助手时崩，**不是权限、不是网络**。判别顺序：先 `gh auth status` 确认有 `repo` scope（排除权限）→ 再看有无崩溃弹窗/`0x0`（是崩溃）。
   - **✅ 根因已定位，零弹窗写法已验证**（控制了变量、连续多次成功）：根因是 Git for Windows 默认的 **`http.sslBackend=schannel` 在非交互 / 沙箱账户下拿不到凭据**（`schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS 0x8009030e`）→ 带 credential helper 时 `git-remote-https.exe` 空指针崩。
     **一眼定性靠用户一句话**：他说「**桌面版从没遇到这个问题**」= 一条免费的控制变量实验 —— **正常用户环境不崩、被唤醒（沙箱）会话必崩** ⇒ 方向钉在「运行账户环境差异」，别在命令行参数上盲试（每崩一次就弹模态框要他手点「确定」）。
     零弹窗写法（三要素缺一不可）：`git -c http.sslBackend=openssl -c http.proxy=http://127.0.0.1:7897 -c credential.helper= push https://x-access-token:<TOKEN>@github.com/<o>/<r>.git main` —— **强制 openssl** + **空的 `credential.helper=`** + **token 写进 URL**。跨账户写过的仓库另需 `git config --global --add safe.directory <repo>`。
   - ⚠️ **`-c credential.helper="!gh auth git-credential"` 必崩**（等约 98 秒 exit 128），别用；**`gh api` / `gh release edit` 走 Go 的 TLS 不受此 bug 影响**。
   - **长期解法（比修 bug 更省事）**：把**出口动作（push / 发 Release）设计成交给正常用户环境执行** —— 被唤醒会话只 commit + 落 patch，push 由桌面侧或另一台 git 正常的主机完成。另外：**能给平台发最后一步的那一侧，往往并不拥有同一个提交** —— 蓝莓侧 clone 改好、commit 完成，却因为本机没配 GitHub 凭据而推不动（`could not read Username for 'https://github.com'`）；**跨 agent 的推送交接，默认是「把改动变成 patch 交给能推的一方」**，不是「先本地 clone 改完再想办法推」。
   - **根治方向**：①上面的零弹窗写法（已验证）；②**SSH 远端 push**（`git@github.com:` 走 22 端口，根本不碰会崩的 https 组件 —— **本环境上网本已配通，2026-10-17 实测 `git push origin main` 一次成功**）；③重装 Git for Windows。判据：**连续 2–3 次无弹窗成功**才算修好，未达标如实说卡在哪。
   - **推不上去不要卡死任务**：把改好的 commit 落成 patch/bundle 到共享目录交接给有可用 git 的一方（如上网本侧）接力推，这就是流水线的价值。
5. **有写权限才推得上去**：给 AI 配的 GitHub token 要有 `repo` scope；平台 App 可能无写权限（拿到 403）→ 此时取"文件包 + 人工合入"方式，别硬 push。
6. **llms.txt 的位置**：放**仓库根**（不是 docs/），且保证能通过 raw 链接直接访问（`https://github.com/<owner>/<repo>/blob/main/llms.txt`）。
