# 截图 → 项目简报

**场景**：刷到好项目，**截图发给 agent**，agent 自动给出**中文简报**。

**触发**：收到截图 + 类似"看看这个""介绍下这个""这个咋样"的意图。

**不是**：把截图内容翻译一遍。**是**：从截图出发，**找到真实项目**，产出**可判断的**简报。

---

## 🔧 能力映射（先看这个 —— 本技能用能力名，不用具体工具名）

本技能只依赖三个**通用能力**。各宿主按自己的工具替换：

| 能力 | 作用 | 常见实现 |
|---|---|---|
| **看图** | 读截图、逐字提取 | 多模态 / 视觉理解工具 |
| **搜索** | 定位项目 | 联网搜索 |
| **读网页** | 抓项目页 / 文档 | 网页抓取 |

**下文一律用「看图」「搜索」「读网页」指代。** 若你宿主工具名不同，自行映射，语义不变。

## ⚠️ 核心纪律（七条，都踩过）

### 1. 截图里的数据**一律不可信，必须回源核验**

短视频/推文的数据**经常注水或过时**。实测案例：

| 来源 | 星数 |
|---|---|
| 截图声称 | 「4.7 万」 |
| 技能旧版写的 | 53.5k |
| **复核时** | **~56k** |
| 结论 | **连技能作者自己写下的数字都会过时 —— 每次都要现查** |

**做法**：截图数据只当**线索**，真实数据**从项目页现读**，简报里**指出差异**。

### 2. 截图里通常**没有** GitHub 地址 —— 必须靠搜索定位

**别指望截图给 URL。** 典型截图只有：项目名 + 一句话描述 + 数据。

**定位方法**（按优先级）：
1. 项目名 + 关键特征词 → 搜索
2. 特征足够独特时（如"某商业产品的开源替代品""支持 646 种语言"），**组合搜索命中率极高**
3. 若项目名太泛（如 "Assistant"），**加上截图独有的数字/描述**缩小范围

### 3. ⚠️ **同名项目很多 —— 必须验证"是同一个"**

**这不是假想风险。** 实测：某项目真的存在**至少两个同名 fork**（不同用户名下的同名仓库）。

**验证三件套**：

| 查什么 | 怎么用 |
|---|---|
| **星数量级** | 截图说几万星 → 找到的账号应该同级，不是几十星 |
| **描述特征** | 语言数、独特卖点要对得上 |
| **创建时间 / 最近提交** | **蹭热度的 fork 通常很新或长期不更新** |
| **commit 活跃度** | **比星数更可信** —— 星数能注水，commit 不能 |

**⭐ 用 commit 活跃度判真伪，而不是星数。**

### 4. 「含AI生成内容」标记 = 提高警惕

截图带这个标记时，**营销话术概率高**。简报要**明确区分**"项目自述"和"我核实的事实"。

### 5. ⚠️ **爆火 ≠ 可用：极年轻的仓库要单独标记**

**高星数 + 极年轻的创建时间** 是病毒式传播的特征，**不等于产品成熟**。实测某仓库：创建仅 10 天、3.5 万星、官方自标 `early alpha`、未决 issue 500+，社区还有"可能是 AI 批量生成"的质疑。

**做法**：看完 `created_at` 与 `open_issues_count` 后，若**创建 < 3 个月**，简报里必须单独提示：
- 创建多久、当前 maturity 标记（alpha/beta/stable）
- 未决 issue 数量（判断维护强度）
- **社区评价**（第三方聚合站 / 论坛 / 视频评论里常藏真话）
- 同一作者下**同时铺开多个同类项目**（多个 sibling repo）是**被质疑批量生成**的信号之一，值得点出

**结论措辞**：这种项目给"**观望 N 个月**"的建议，别给"值得上"。

### 6. ⚠️ **开源的是壳，能力在付费 API 后面 —— 必须说清"能不能白嫖"**

**MIT 许可证不等于免费可用。** 实测某项目：仓库 MIT、`SKILL.md` 写得完整漂亮、还明确支持多种 agent 宿主，**但 README 第 2 步就是：**

```bash
<cli> config set app_key <your_app_key>
# 需 API key？请联系 xxx@yyy.com
```

**判据 —— 翻 README 时专找这三类信号**：

| 信号 | 含义 |
|---|---|
| 要求 `app_key` / `api_key` / `token`，且**不是自带的** | 核心能力在**外部商业服务**，仓库只是客户端 |
| 要**邮件申请** / 扫码 / 加好友 / 注册某站点 | 引流型项目，多半**收费或有配额** |
| 仓库里只有 skill 定义 / CLI 壳，**没有核心实现** | 开源的只是「说明书」 |

**简报写法**：把「开源的是 X，收费/需授权的是 Y」**分开写清**，别让用户以为 clone 下来就能用。
措辞例：「开源的是**技能定义（SKILL.md + references）**；核心是**商业 API 服务**（`openapi.<domain>`），需申请 app_key」。
并补一句**成本提示**：这种项目「先看 API 是否收费再谈试用」。

⚠️ 别把这类项目归到「爆火≠可用」（纪律 5）那条 —— 它的代码可能是真实、活跃、成熟的，
**误导点不在成熟度，在授权与成本**，两回事要分开报。

### 7. ✅ **格式对齐是加分项，值得写进简报**

项目若采用**通用约定**（如技能用 `SKILL.md` + YAML frontmatter、支持主流 agent 的技能目录、
`topics` 里直接列了常见工具名），**明确点出来** —— 这比笼统说「支持很多工具」有用得多，
用户据此判断能不能直接复用。

实测已遇到多个走 `SKILL.md` + frontmatter 的项目 —— 这个格式已事实标准化，
遇到时可直接说「**格式是标准的，clone 进技能目录即可**」。

## 📋 五步流程

### 第一步：看图，逐字提取

别漏：
- 项目名（**最重要**）
- 一句话描述 / 核心卖点
- 数字（星数、语言数、用户数）
- 发布者、平台线索
- ⚠️ **有没有 GitHub URL 或用户名**

**产出**：一张"截图原始信息"清单。

### 第二步：搜索定位项目 → 读项目主页

```
搜索式：<项目名> <关键特征> github
例：<产品名> 开源替代品 本地 部署
```

**命中后立即读项目主页**，拿：
- **真实星数 / forks / commits / 最近提交时间**（现查，别用缓存印象）
- 许可协议
- 技术栈
- README 的定位描述

**⚠️ 用上面「验证三件套」确认就是截图那个。**

**⚠️⚠️ 星数只认 API，别认网页** —— GitHub 的 HTML 页面会**显示被缓存的旧数**（实测某仓库网页显示 516 星，API 返回 35,305 星，**差 68 倍**）。抓网页拿到的星数可能是几个月前的快照，据此写简报会严重低估。**数字一律走 API**：

```bash
curl -s "https://api.github.com/repos/<owner>/<repo>" \
     -H "User-Agent: curl/8.5.0" -o /tmp/repo.json
# 取 stargazers_count / forks_count / created_at / pushed_at
#   / license.spdx_id / open_issues_count / topics
```

网页只用来读 README 与目录结构；**所有数字以 API 为准**。若两者不一致，简报里报 API 值并注明差异。

### 第三步：深挖关键信息（按需）

| 要判断什么 | 去读哪 |
|---|---|
| 能不能装在我的机器上 | `docs/performance.md`、`docs/install/*`、README 的 Requirements |
| 许可是否可商用 | `LICENSE`、README 的 License 段 |
| 有没有官方 skill/插件 | 仓库的 `skills/`、`.claude/`、`.agents/` 目录 |
| 安全/合规风险 | `SECURITY.md`、`PRIVACY.md` |
| **真实活跃度** | 提交历史、最近 release、issue 响应速度 |

### 第四步：**结合使用者环境判断**（精华，别省）

**光介绍项目没用，要说清"对使用者意味着什么"。**

必答三问：
1. **硬件吃得消吗？**（对照 CPU / 内存 / 显卡 / 网络条件）
2. **装在哪台机器合适？**（决策表比描述更有价值）
3. **跟现有工具冲突吗？**（有没有重复造轮子）

> 说明：本步骤**依赖 agent 对使用者运行环境的了解**。
> 若你的宿主没有环境上下文，就把这三问**作为待确认项列给用户**，别略过、也别凭空编造环境。

### 第五步：出简报（模板见下）

## 📄 简报模板

```markdown
## <项目名>

**一句话**：<项目自述的定位，标注是"自述">

**上游**：`github.com/<owner>/<repo>`
**真实数据**：⭐ <真实星数> · fork <n> · 最新提交 <日期> · <许可>
**⚠️ 与截图差异**：<如截图说 4.7万 实际 56k；无差异就删这行>

### 它是什么
<两三句，说清核心能力>

### 🎯 对使用者的意义（最重要）
<硬件判断 + 装哪台机器 + 跟现有工具关系>

### ⚠️ 要注意的
<许可陷阱、营销话术、资源要求>

### 结论
<值得/不值得看，下一步建议>
```

**模板要点**：
- **必填「最新提交日期」** —— 星数会注水，**commit 活跃度骗不了人**
- 数据**现查现写**，别用印象值

**篇幅纪律**：即时通讯场景**短**。先结论，细节按需展开。

## 🚫 反模式

| 反模式 | 为什么 |
|---|---|
| 把截图内容**复述一遍**当简报 | 那是搬运，不是分析 |
| 直接采信截图数据 | 常注水/过时，**必须回源** |
| **星数从 GitHub 网页上抄** | **网页会显示缓存旧值**（实测差 68 倍）→ **一律走 API** |
| **引用自己记过的旧数字** | **连作者自己写的都会过时**（实战踩过） |
| **高星=推荐** | **爆火 ≠ 可用**；极年轻仓库（<3月）给"观望"，不给"值得上" |
| 只介绍项目，不说**对使用者是否合适** | 用户要的是**决策依据**，不是百科 |
| 拿截图里的 AI 生成描述当事实 | 标注区分"自述"与"核实" |
| 项目名太泛时不加特征词搜索 | 会搜到同名无关项目 |
| **搜到同名项目不验证就采信** | **真有同名 fork，会搜错** |
| **以为 MIT/开源 = 免费可用** | **开源的可能只是壳**，能力在付费 API 后面（纪律 6） |
| 看到"支持某工具"就以为能直接用 | 支持安装 ≠ 免授权可用，**仍要查 API key** |
| 长篇大论讲原理 | 即时通讯场景要短 |

## ✅ 实战案例（均已脱敏，2026-10 实测）

### 案例一：本地语音克隆工具

**输入**：短视频截图（项目名 + "某商业产品替代品" + "支持 646 种语言" + 本地运行，无 URL，标"含AI生成内容"）

**执行**：
1. 看图逐字提取 → 项目名 + 特征词
2. 搜索「开源 本地 语音克隆」→ 命中目标仓库
3. 读主页 → 星数 53.5k（**截图说 4.7万**，纪律 1 命中）
4. 深挖 `docs/performance.md` → GPU / VRAM 硬性要求
5. 环境判断 → 列出"本机是否吃得消"

**复核时发现的新规律**：
- ⚠️ **星数已涨到 ~56k** → 强化纪律 1（每次现查）
- ⚠️ **发现两个同名 fork** → 催生纪律 3
- ✅ 许可（AGPL-3.0）属实、官方 skill 目录确实存在

### 案例二：Rust 写的图像编辑器

**输入**：短视频截图，标题党（"炸穿某商业软件"），**无 URL**，标"含AI生成内容"

**执行**：
1. 看图逐字提取 → 项目名 + 特征（Rust 编写、图层面板）
2. 搜索命中目标仓库
3. 主页读到星数 **516** —— 但直觉不对，转 **API 复核 → 35,305**（网页缓存旧值，**差 68 倍**）
4. 深挖 → `created_at` 只有 **10 天**、`open_issues` **509**、官方自标 `early alpha`
5. 查社区评价 → 有评论直指"可能是 AI 批量生成"
6. 结论给"**观望 1-2 月**"

**跑出的新规律**：
- **星数只信 API，不信 HTML 页**（纪律 2 补充）
- **爆火 ≠ 可用**（纪律 5）
- **同名风险重现**：第三方聚合站上列着另一个名字很像的条目，印证纪律 3
- ⚠️ **没跑通的地方如实写**：该仓库**未实际试用**（硬件不满足 + alpha），
  简报里明确写"没上手"，**不编造体验**

### 案例三：教育类平台 + 视频解说技能包（同日两条）

**A. 某高校实验室的开源学习助手**
- 截图报 3.83 万星 → **API 实测 41,136**（已涨，纪律 1 再现）
- 定位靠机构名 + 实验室名，描述特征唯一，一次命中
- 亮点：技能体系**走的也是 `SKILL.md` + YAML frontmatter**（纪律 7）
- 数据完备：`created_at` / `open_issues` / `pushed_at` / `topics` 全拿到，**结论可直接给**

**B. 某影视解说 CLI 技能包**
- 定位极顺利（仓库名在截图里就有）
- **本次新规律**：README 要求 `app_key` + 邮件申请 ⇒ **纪律 6 诞生**
  （此前从未把"开源外壳 + 付费核心"单列成一条规则）
- 另一观察：`topics` 里列了常见 agent 工具名、安装说明直接给技能目录 ⇒ **纪律 7**
- 时间线线索：创建 3 月、**最后一次推送 7 月**（比截图热度冷很多）
  → 引用时带上，帮用户判断活跃度

**同日连续作业的用法**：第一条的经验**直接喂给第二条**（B 就是在 A 之后才发现
"授权 / 成本"这个角度没被覆盖），**并把新规律当场写回技能**，别等下次。
