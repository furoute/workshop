# 多智能体协作（Multi-Agent Collaboration）

## 什么时候用

- 一个任务需要**多个 agent** 分工（写代码 / 写文档 / 审查 / 测试）；
- 想让**另一个 AI 审另一个 AI 的产出**（减少幻觉与返工）；
- 需要**跨机器/跨通道**派活（有的在群里，有的要单线私信）。

**不适用**：一次对话就能做完的事、纯机械执行、需要人实时互动的事。

---

## 第零步：人的位置（先讲清，否则没人知道听谁的）

```
人  →  只对接 Dispatch（调度方）
       ↓
       Dispatch  →  其余所有 agent
```

**规矩**：

1. **人只出需求，不参与执行**；也不直接指挥 Execute / Review。
2. **其余 agent 不直接找人** —— 有事找 Dispatch，由 Dispatch 汇总后再报到人。
3. **⚠️ 需求可能是分多段到达的**：

   > 语音消息有**时长上限**（例如微信语音约 60 秒），一句话说不完时，人会分多条发，
   > 并明确提示"**没结束 / 继续**"。Dispatch 必须判断**是否说完了**，
   > 未说完就**等**，**不要拿第一段当完整需求就开工**。

4. **人只收一条结论** —— Dispatch 汇总后一次报告，不让人去翻多个 agent 的对话。

---

## 一、角色设定（核心）

协作的质量取决于**角色边界清不清**。四种基本角色：

| 角色 | 职责 | 不该做的 |
|---|---|---|
| **Dispatch（调度方）** | 把人的口语需求 → 结构化任务单；分发；催收；**只把结论回报给人** | 不亲自写正文、不替别人做决定 |
| **Execute（执行方）** | 按任务单干；产出落盘；**完事必须回报** | 不擅自扩大范围、不默默改需求 |
| **Review（复审方）** | **以"陌生者视角"验一遍**：照文档能不能做、命令能不能跑、有无遗漏 | 不自己动手改，只出意见 |
| **Arbitrate（仲裁方）** | 当两方观点冲突时，**用实测/证据裁定** | 不以"感觉"判对错 |

### 角色绑定的边界（最容易搞错）

- ✅ **Dispatch 与 Arbitrate 可以是同一个 agent**（调度方天然中立，**前提是它自己没有下场执行**）；
- ❌ **Dispatch 与 Execute 不能是同一个**（派活的人不该自己干，否则没人复核）；
- ❌ **Review 与 Execute 不能是同一个**（等于自己审自己，抓不出问题）；
- ❌ **Arbitrate 必须是争议双方之外的第三方** —— 若 Dispatch 本人参与了 Execute/Review，
  **它就不能当仲裁方**，必须另找一个中立的 agent。

## 二、三种通道

| 通道 | 用于 | 怎么用 |
|---|---|---|
| **群内广播** | 需要多方知悉、公开留痕 | 发一条所有人都能看到的通知；所有 agent 可见，冗余但透明 |
| **单线私信** | **只问某一个 personal agent**（不打扰其他人） | **点对点发给指定 agent，不经群聊**；内容**仍落成任务单格式**；**收到即回执** |
| **CLI 直调** | 同一台机器上的 agent 互相唤醒 | 直接命令行拉起，**一轮制** |

**选择原则**：
- **需要多方协作/知悉** → 广播；
- **只问某一个专家意见** → 单线私信；
- **同机、要即时** → CLI 直调（**一轮制**，禁止来回闲聊）。

### CLI 直调的命令格式（内容留空，按需填）

> ⚠️ **以下命令均以本机 `--help` 实测为准；换环境请先跑 `--help` 确认**。
> 不同版本的参数会变，照抄前务必核对。

```bash
# Hermes（本机调度方）—— 已实测
hermes -z "<提示词>"                  # 一次性执行（长文本建议走文件 + stdin 重定向）
hermes --continue                     # 续上一次会话
hermes --resume <session-id>          # 续指定会话

# Codex CLI（执行方：写代码）—— 已用 codex --help 实测核对
codex exec --sandbox workspace-write \
  --add-dir <可写目录1> --add-dir <可写目录2> \
  -C <独立工作目录> \
  "<任务内容>"

# DSH（DeepSeek Harness，执行/文档方）—— ⚠️ 以本机 dsh --help 为准
dsh --profile headless - <<'EOF'
<任务内容>
EOF

# OpenClaw（支援/复核方）—— 已实测有 agent 子命令
openclaw agent --message "<任务内容>" --timeout <秒>
#   其他参数（--agent / --channel / --deliver 等）见 openclaw agent --help
```

> ⚠️ **通用要点**：
> - **长文本走文件或 stdin**，不要塞进命令行参数（中文/特殊字符会被 shell 弄坏）；
> - **一轮制**：一次提问 → 一次回答 → 结束，不要来回追问；
> - 同机多个 agent 并存时，**别共用工作目录**（会互相覆盖、抢写权限）；
> - **换版本先看 `--help`** —— 参数是最容易过时的东西。

## 三、Workflow（五步 + 返工闭环）

```
第零步  人 → Dispatch（需求可能分多段）
   ↓
① 需求 → 任务单（Dispatch 整理）
   ↓
② 分发 + 唤醒（广播 / 私信 / CLI）
   ↓
③ 执行 + 落盘（Execute）
   ↓
④ 交叉复审（Review，以"陌生视角"）→ 意见落文件
   ↓
   ├─ 复审通过 ──────────→ ⑤ 汇报（Dispatch → 人，一条）
   │
   └─ 复审发现问题 ──→ 退回 ③（Execute 修正）
                          ↓
                     ①' 复验（Review 只验改动点）
                          ↓
                     ├─ 通过 → ⑤ 汇报
                     └─ 仍有问题 → 再退回（限 2 轮）
                                    ↓
                          2 轮仍不过 → 仲裁（⑤）或上报人决策
```

**返工闭环的三条规矩**：

1. **复审意见必须落到文件**（哪一条不通过、要改成什么），Execute 照着改，不靠口头传；
2. **复验只验改动点**，不重跑全文（省时间，也避免"越改越乱"）；
3. **限 2 轮** —— 两轮还不过，说明**任务单本身有问题**，交给仲裁或上报人，
   **不要无限来回**（那正是最烧 token 的死循环）。

### 仲裁后也要闭环

仲裁判某一方错 → **错的那方按裁定修正 → 复验一次 → 才结案**。
**仲裁不是终点，是"回到 Execute 再走一遍"的起点。**

### ① 任务单要写清什么

```
【谁 → 谁 · 任务标题】

■ 背景（为什么做、前情）
■ 要办什么（可核对的清单，不是"你看着办"）
■ 红线（不许做什么 —— 尤其保密、不动别人的文件）
■ 交付物（落在哪、什么格式）
■ 验收标准（怎么算完成）
```

**反面教材**："帮我改改文档" —— 没有边界，执行方只能猜。

### ② 分发与唤醒

- **异步**：丢进共享目录/消息通道，对方自行拉取；
- **同步**：CLI 直调或信令唤醒，**一轮制**（一问一答即止）；
- ⚠️ **唤醒后必须盯到回执**，不能"丢完就走"（见下节）。

### ③ 执行方的纪律

- **只改该改的**，不顺手重构；
- **所有产出落盘**（不要只在对话里说）；
- **完事必须发回执**（含：做了什么、在哪、怎么验证的）。

### ④ 复审方的"陌生者视角"

**这是最容易被省略、但价值最高的一步。**

复审方要假设自己**从没参与过**，然后：
1. **照文档走一遍** —— 命令能不能直接抄？有没有跳步必挂？
2. **逐条对源码/事实** —— 数字对不对？指向对不对？
3. **找"黑盒感"** —— 某一步做了事，但读者不知道发生了什么；
4. **报忧不报喜** —— 没意见就说"OK"，别硬凑。

> **复审不是"看看"，是"跑一遍再说话"。**
> 凡涉及"会不会卡/报什么错"的结论，**必须实跑或读到确切分支**，不许用推理冒充实测。

**复审意见落文件，不进对话** —— 方便追溯，也不占上下文。

### ⑤ 仲裁

两方各执一词时，**第三方实跑一遍**，用输出定胜负：

```
主张 A：这样做会报错
主张 B：不会，会静默通过
   ↓
第三方实跑 → 看退出码 + 输出
   ↓
按事实裁定，输的一方认错
```

**仲裁方中立**：不站队，只看证据。

## 四、三条铁律

### 1. 唤醒后必须盯守 + 主动回报

- **发出的方**：盯到回执为止；**完成/超时都主动告诉人**，不能让人来问；
- **被唤醒的方**：干活期间保持"处理中"可见状态，**完成后必须发回执**；
- **一句话**：**"要么看得见在处理中，要么完事必有回音"——二选一必须有一个。**

### 2. 单写者原则

**谁的文件谁写**。不要在别人的机器上改别人的文件 —— 发任务 + 唤醒，让它自己改。

### 3. 一轮制，禁止闲聊

- 需要讨论的，**一次说清**；
- **不要来回追问**（每多一轮就是多烧一份 token）；
- 需要多方意见的，**一次广播**收齐。

## 五、名字处理（对外发布的规矩）

- **对外文档**里，用 **agent 产品名**：Hermes / OpenClaw / Codex / DSH / Muse；
- **不写内部昵称、代号、人名** —— 昵称只在内部有语境，对外没有意义；
- ⚠️ **但产品名在多机部署时不唯一**（你可能有两台机器都跑 Codex）。

**⇒ 规则**：

| 场景 | 用什么 |
|---|---|
| 对外文档、文章、技能说明 | **产品名**（Codex、Hermes）|
| 实际寻址、派活、路由 | **唯一 agent ID**（如 `codex-desktop`、`codex-laptop`）|
| 写任务单的"收件人" | **唯一 ID**，并在括号里标产品名（如 `codex-desktop`（Codex））|

**理由**：产品名是给人看懂的，唯一 ID 是给系统执行的。**两者都要有，但别混。**

## 六、交付物与留痕

| 东西 | 放哪 | 为什么 |
|---|---|---|
| **任务单** | 消息通道（可检索） | 事后能追"当时让人做什么" |
| **产出** | 共享目录 / 仓库 | 不依赖对话历史 |
| **回执** | 消息通道 | 证明"真的做了" |
| **复审意见** | 文件 | 可追溯，不占上下文 |
| **仲裁记录** | 落盘 | 同类争议下次可查 |

**留痕原则**：**"信发了、账没记"等于没做** —— 所有对外动作都要有可查的记录。

## Pitfalls

1. **Review 和 Execute 是同一个 agent** → 等于自己审自己，抓不出问题；
2. **复审方只读不跑** → 得出"读代码想象出来的报错"，误判（**必须实跑**）；
3. **任务单没有验收标准** → 执行方不知道做到什么程度算完；
4. **多方同时改同一份文件** → 冲突。用**分支**或**分文件**隔离；
5. **唤醒了不盯** → 人不知道任务何时结束，体验倒退；
6. **只在对话里说结果，不落盘** → 会话一结束就丢；
7. **把人当"另一个可点名的 agent"** → 人只跟 Dispatch 对接，不该被直接派活；
8. **多段需求只收到第一段就开工** → 做错方向，返工。
