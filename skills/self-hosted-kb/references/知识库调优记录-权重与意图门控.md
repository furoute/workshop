# 知识库调优记录 · 权重与意图门控

**记录时间**：2026-10-26
**触发原因**：查「<供应商> BBU 电池更换」返回的全是 Disk 更换方案，一条 BBU 都没命中；而 Everything 不到 1 秒就查出 10 条。

---

## 一、问题现象

| 查询 | 改前结果 |
|---|---|
| `<供应商> 电池模组 更换` | 返回 4 条「<型号A>/<型号B> **Disk** 更换实施方案」，0 条 BBU |
| `BBU`（直接查库 FTS5） | 能命中 10 条 ✅ |

**⇒ 结论：不是数据缺失，是排序被淹没。**

```
三库所有通道统一取 100-500 条候选
⇒ 正文/向量通道吐出上千条候选
⇒ 文件通道只占 RRF 的一份票
⇒ 几百条正文把 10 条文件结果压到第 49 名之后
```

---

## 二、调优思路：两条路并行

### 路 1：识别「文件意图查询」（意图门控）

**⇒ 核心洞察：短查询词（BBU / <型号> / 2011.11.23）本质是「找文件」，不是「问内容」。**

**⇒ 这两类查询应该走完全不同的召回策略。**

---

### 路 2：动态权重 + 收窄候选集

**⇒ 文件意图时，不是简单提高权重，而是把正文候选从 500 条压到 20 条。**

**⇒ 从「提高分母」改成「缩小分母」。**

---

## 三、文件意图的判定规则

### 命中任一强信号即进入文件模式

```python
# 1. 扩展名或路径分隔符
FILE_INTENT_PATTERN = re.compile(
    r"(?:[\\/]|\.[A-Za-z0-9]{1,8}\s*$|"
    r"\b(?:windows|ubuntu|centos|debian|redhat|rocky|alma)\b.*\d|"
    r"\b[A-Za-z][A-Za-z0-9_.]*[-_]\d)"
)

# 2. 设备型号（忽略 - _ . 空格 等分隔符）
FILE_INTENT_MODEL_PATTERN = re.compile(
    r"(?<![A-Za-z0-9])[A-Za-z]{2,}[_-]?\d+[A-Za-z0-9_-]*(?![A-Za-z0-9])",
    flags=re.IGNORECASE,
)
# <型号> / <型号> / <型号> 都能识别

# 3. 日期（2011.11.23 / 2011-11-23 / 2011_11_23）
FILE_INTENT_DATE_PATTERN = re.compile(
    r"(?<!\d)(?:19|20)\d{2}[./_-](?:0?[1-9]|1[0-2])"
    r"[./_-](?:0?[1-9]|[12]\d|3[01])(?!\d)"
)

# 4. 工单号（8 位以上连续数字）
FILE_INTENT_ORDER_PATTERN = re.compile(r"(?<!\d)\d{8,}(?!\d)")

# 5. 大写缩写（BBU / HBA / ISO）
FILE_INTENT_ABBREVIATION_PATTERN = re.compile(
    r"(?<![A-Za-z0-9])(?=[A-Z0-9]*[A-Z])[A-Z][A-Z0-9]{1,7}(?![A-Za-z0-9])"
)
FILE_INTENT_EQUIPMENT_ABBREVIATIONS = {"BBU", "HBA", "MOD1"}
```

### 但是：必须有「语义标记」抑制

```python
# 含以下中文词时，不当作文件查询
FILE_INTENT_CONTENT_PATTERN = re.compile(
    r"(?:内容|查询|如何|怎么|介绍|说明|原理|配置|故障|方案)"
)
```

**⇒ 逻辑：**

```python
def query_has_file_intent(query: str) -> bool:
    tokens = file_query_tokens(query.strip())
    
    # 强信号直接判定
    if 扩展名 in tokens: return True
    if 路径/系统名.search(): return True
    if 日期.search(): return True
    if 工单号.search(): return True
    if 型号.search(): return True
    
    # 缩写：命中设备缩写直接 True
    abbreviations = 提取大写缩写(query)
    if abbreviations & {"BBU","HBA","MOD1"}: return True
    
    # 一般缩写：1-3 个词 + 含大写 + 无语义标记
    return len(tokens) <= 3 and abbreviations and not 语义标记.search(query)
```

**⇒ 举例：**

| 查询 | 判定 | 原因 |
|---|---|---|
| `BBU` | file | 设备缩写 |
| `replace BBU` | file | 设备缩写 |
| `<型号>` | file | 型号 |
| `2011.11.23` | file | 日期 |
| `14369736 98205259` | file | 工单号 |
| `<项目域> <子域> 内容查询` | semantic | 含「内容」「查询」 |
| `<城市> 医疗客户 存储` | semantic | 无文件名特征 |

## 四、动态权重（RRF）

### 权重常量

```python
FILE_INTENT_EXACT_WEIGHT           = 10.0   # 文件名/路径/目录精确匹配（文件意图）
FILE_INTENT_COMPLETE_MATCH_WEIGHT  =  9.0   # 完整文件名匹配（文件意图）
FILE_INTENT_MATCH_WEIGHT           =  8.0   # 型号/缩写/日期/工单号命中（文件意图）
FILE_INTENT_FILE_WEIGHT            =  5.0   # 其他文件 FTS 候选（文件意图）

FILE_EXACT_WEIGHT                  =  3.0   # 精确匹配（语义查询）
# 文件 FTS 语义查询：0.7（无匹配）/ 3.0（完整文件名匹配）
# 元数据通道：2.5
# 正文/向量通道：1.0
```

### 对照表

| 通道 | 语义查询 | 文件意图查询 |
|---|---:|---:|
| 文件名/路径/目录精确 | 3.0 | **10.0** |
| 完整文件名匹配 | 3.0 | **9.0** |
| 型号/缩写/日期/工单号 | — | **8.0** |
| 其他文件 FTS | 0.7 | **5.0** |
| 元数据 | 2.5 | 2.5 |
| 正文 FTS | 1.0 | 1.0 |
| 向量 | 1.0 | 1.0 |

**⇒ 注意：正文和向量的权重没动，动的是文件通道和候选集。**

## 五、候选集收窄（这是关键）

### 语义查询（保持不变）

```python
text_candidate_limit = min(500, max(100, top_k * 10))
file_candidate_limit = min(500, max(100, top_k * 10))
```

### 文件意图查询

```python
text_candidate_limit = 20                                    # 正文只取 20 条
file_candidate_limit = min(100, max(50, top_k * 5))          # 文件取 50-100 条
```

**⇒ 这一步才是根治：**

```
改前：正文 500 条 + 向量 500 条 淹没 文件 50 条
改后：正文 20 条 + 向量 20 条 让路 文件 50 条
```

**⇒ 从「提高语料权重」变成「缩小竞争范围」。**

### 附带优化：文件意图时只取 catalog-v2

```python
use_catalog_for_files = file_intent and any(
    d.source_id == "catalog-v2" for d in datasets
)
# 避免 others-v1 里的重复路径占位
```

## 八、顺手修的三个边界

### 1. 型号分隔符不一致
```
问题：<型号> 查不到 <产品线>_<型号> Procedures.docx
修法：型号匹配时忽略 - _ . 空格
效果：<型号> → 命中 <产品线>_<型号> Procedures.s - 1.docx
```

### 2. 裸扩展名查询
```
问题：单独查 ISO → 返回 iso2022jp.go（源码）
修法：识别「裸扩展名」时优先按 extension='.iso' 过滤
效果：查 ISO → 优先列出 .iso 镜像
```

### 3. 重复路径占位
```
问题：同一文件同时在 catalog-v2 和 others-v1，占掉两个位次
修法：文件意图时只取 catalog-v2 文件通道
```

## 九、可复用经验

### 1. 检索排序问题的三种解法和取舍

```
提高权重     ← 简单，但权重再高也拼不过数量优势
缩小分母     ← 有效，让竞争通道少吐候选
意图分流     ← 最彻底，不同查询走不同策略
```

**⇒ 本次用了后两种，效果最好。**

### 2. 「短查询词」不等于「文件查询」

```
BBU         → 是缩写，可能是设备，也可能是文件名
BBU 是什么  → 含「是什么」，是语义查询
⇒ 必须用语义标记做抑制
```

**⇒ 只靠长度判断（1-3 个词）会误伤。**

### 3. 调优必须有回归验证

```
改前先记录语义查询的排序
改后再跑一遍
⇒ 确认「没退化」才算成功
```

**⇒ 本次固定验证两条语义查询：`<城市> 医疗客户 存储`、`<项目域> <子域> 内容查询`。**

### 4. 验收要串行，不能并发

```
并发测延迟会争用模型锁
⇒ 测出 211 ms，误判为超时
⇒ 所有性能数据必须串行跑
```
