## 五、技术要点

### 1. 为什么能做到 60-90 ms
```
① 模型常驻（只加载一次，省 1-8 秒）
② 向量一次读进内存（561 MB，32GB 内存充裕）
③ FTS5 连接常开（不每次重连）
④ 查询编码 batch=1（不做过度批处理）
```

### 2. 向量检索为什么是 45 ms
```
对全量向量做精确余弦相似度计算
402,638 + 153,926 ≈ 55 万条 × 512 维 float16
⇒ NumPy 矩阵运算，一次约 45 ms
⇒ 没有用 ANN 索引（HNSW/IVF），所以是精确解，无近似误差
```

**⇒ 这个规模下暴力搜索完全够用，不需要引入向量数据库。**

### 3. 三路召回 + RRF 融合
```
chunk_fts    字面命中（FTS5 trigram）
vector       语义命中（BGE 512 维余弦）
metadata     文件名/路径/客户名/案例名命中

三路各自排名 → RRF 倒数排名融合 → 统一排序
RRF 只需要 2 ms
```

## 六、与云端方案的对比（参考）

| 维度 | 本地方案 | 云端 API |
|---|---|---|
| 单次查询延迟 | 60-90 ms | 300-1500 ms（网络往返） |
| 单次成本 | ~0（电费） | 0.004 元/次 |
| 数据出网 | 不出 | 全部出网 |
| 断网可用 | 是 | 否 |
| 索引规模上限 | 内存（32GB 约 600 万条） | 无限（但要付费） |
| 模型升级 | 手动换模型 + 重建 | 换 API 版本即可 |

## 七、复现方法

```powershell
cd <工作区>\kb_query_service

.\start.ps1          # 启动服务
.\status.ps1         # 查看状态

# 10 连查性能测试
<知识库根>\<快照>\.venv\Scripts\python.exe .\benchmark.py

# 功能验收
<知识库根>\<快照>\.venv\Scripts\python.exe .\acceptance_test.py

# 直接查询

.\stop.ps1           # 停止服务
```

## 八、局限与后续

**当前局限：**
```
· others-v1 只有 130 份样张正文（正文补库还没跑）
· 向量检索是暴力计算，规模到 300 万条以上会明显变慢
· 单机服务，没有并发压测
```

**后续计划：**
```
① 正文补库第一批（约 3,898 个 PDF/Office）
② 并发压测（10/50/100 QPS）
③ 规模到 300 万条以上时评估 FAISS/ANN
④ 可选：接入本地大模型做 RAG 生成
```
