# 自建知识库：FDE 实践复盘（三天全记录）

**时间跨度**：2026-10-23（周五）— 2026-10-26（周一）
**性质**：一次完整的 Forward Deployed Engineer 式落地实验
**结论先行**：用三台自有设备（一台生产主机、一台算力节点、一台控制台）+ 本地模型 + 本地索引，把一个 33 GB、6,657 份文件的语料，做成 40 万块的可用知识库，热查询 100 ms 级。框架、软件、硬件、成本四个方面的问题全部趟过一遍。

> 本文只讲方法论。项目名、目录位置、客户信息一律不写。

## 一、为什么要自己做

技术大拿提了两条建议，我们把它当了施工图：

```
① 真正的知识库，RAG 不能少
② 可以用对象存储的特性做「零数据库」，靠 meta + etag 就够
```

两条我们都没照抄，但都消化了：

```
关于 RAG
  → 做，但拆开做：关键词一路、语义一路，不迷信单路
关于「零数据库」
  → 没做对象存储，但吸收了它的核心思想：
    原文件只读、不搬动、不复制
  → 索引独立成库，坏了可以重建
  → 只有 3,932 条文件目录 + 一个 SQLite，就是「薄数据库」
```

**⇒ 一句话：不做重，做薄；原文件原位，索引可弃可重建。**

### 1.1 索引放 SSD，这一条比什么都重要

**⇒ 这是整件事里最容易被忽略、但收益最确定的一条。**

```
数据盘（机械硬盘）  语料放这里，几十 GB，不用动
系统盘（固态硬盘）  索引放这里，SQLite + FTS5 + 向量

为什么：
  FTS5 是随机读密集
  机械盘上每次查询要等磁头寻道
  固态盘上直接命中页缓存

⇒ 索引和语料分离，是「快」和「便宜」同时成立的前提
  语料几 TB 便宜地放着
  索引几百 MB 放在贵的地方
```

**⇒ 实测差别：**

```
索引在机械盘：热查询有几百毫秒的抖动，冷查询更慢
索引在固态盘：热查询稳定在 100 ms 级
```

**⇒ 别因为「盘大」就把索引放过——这是最常见的一次性错误。**

## 二、架构：三台机器，三种角色

### 2.1 硬件（自有设备，不是旗舰算力）

| 角色 | 定位 | CPU | 内存 | GPU | 存储 |
|---|---|---|---|---|---|
| 生产主机 | 仓库 + 常驻服务 | 6 核 12 线程 | 32 GB | 6 GB 显存（上代中端） | SSD 465 GB + HDD 1.8 TB |
| 算力节点 | 批量计算 | 24 核 32 线程 | 32 GB DDR5 | 8 GB 显存（移动版） | NVMe 1 TB |
| 控制台 | 协调 + 分发 | 4 核 | 8 GB | 无 | 小容量 |

**⇒ 设计要点：**

```
· 算力节点不是常开的，插电 + 网线时才上岗
· 生产主机必须 24×7，因为它挂着常驻服务
· 控制台最弱，只跑协调逻辑，不碰重活
· 索引放 SSD，语料放 HDD —— 这个分离很关键
```

**⇒ 为什么索引必须放 SSD：**

```
FTS5 是随机读密集
HDD 上每次查询要等磁头
SSD 上直接命中页缓存

实测：索引放 SSD 后，热查询从「几百毫秒级抖动」
      变成「100 ms 级稳定」
```

### 2.2 软件分工

```
生产主机（Codex）
  · 扫描 / 去重 / 分类
  · 建 FTS5 索引
  · 建向量库
  · 常驻查询服务（HTTP :8756）
  · 后期切块兜底

算力节点（Codex）
  · 早期：抽取 + 切块
  · 中期：embedding（GPU）
  · 后期：整批打包回传

控制台（Hermes）
  · 接需求
  · 拆任务、分发
  · 汇总结果
  · 初筛判断
```

### 2.3 通信方式

```
控制台 → 生产主机/算力节点    ACP 信箱 + SSH 唤醒（间歇）
生产主机 ↔ 算力节点           千兆网线 / SMB（一次性快照）
控制台 → 生产主机查询服务      HTTP，常驻
控制台 ↔ 生产主机             文件同步（常驻）
```

**⇒ 一个反直觉的决定：**

```
❌ 不用 scp 传文件、不用远程执行二进制
✅ 只传「需求单」，让对端 agent 自己读、自己干、自己回执
```

**⇒ 因为 agent 之间传「意图」，比传「动作」更稳。**

## 三、两条路并行

### 路 1：本地 RAG（拆开做）

```
语料 33.6 GB / 6,657 文件
    │ 去重（SHA-256）→ 6,427 / 32.45 GB，重复 230
    │
    ├─ 抽取：PDF / Office / OCR，CPU 多进程
    ├─ 切块：400 字 / 50 重叠 → 402,638 块
    ├─ 索引：FTS5 倒排（关键词一路）
    ├─ 向量：512 维 embedding（语义一路）
    └─ 融合：RRF（两路投票）
```

**⇒ 关键认知：FTS5 和向量不是替代关系，是两条腿。**

```
FTS5     查「字面」，快、准、可解释
embedding 查「语义」，能找同义、跨表述
RRF      两路各出候选，按名次投票融合
```

### 路 2：整段任务交给算力节点

```
不是「远程调用一个函数」，而是：
  → 把任务整包扔过去
  → 它在本地自己跑完
  → 结果打包回传

好处：
  · 34 GB 语料不用来回搬
  · 算力节点 24 核可以吃满
  · 生产主机不被打断
```

**⇒ 这本质上就是「按需租用算力」，只不过租的是自己桌上那台。**

```
大厂：旗舰 GPU / 光纤 / RDMA
我们：一台笔记本 + 一根千兆网线
原理完全相同：数据过去 → 算完 → 结果回来
```

## 四、实测：CPU 满载 vs GPU 上岗

这是最有价值的一段，因为它是被监控数据逼出来的认知。

### 4.1 什么时候 CPU 满载

```
抽取阶段（PDF/Office/OCR）
  → 多进程 + 多线程，CPU 24 核全部吃满
  → GPU 占用 0%，温度、功耗都不动
  → 用户现场看到「CPU 100%，GPU 0%」以为出了问题

原因：
  · 文本解析是纯 I/O + 字符串处理，没有矩阵运算
  · Office 解析（尤其是老格式）走的是 COM / 单线程
  · OCR 是 CPU 密集（除非用 GPU 版推理）
```

**⇒ 结论：抽取阶段，GPU 帮不上忙，堆 CPU 核数才是正解。**

### 4.2 什么时候 GPU 才上手

```
embedding 阶段
  → GPU 才真正开动
  → 4 万块向量在 GPU 上几十分钟
  → 在 CPU 上要几小时
```

**⇒ 所以整条流水线的形态是：**

```
CPU 满载（抽取/切块） ──▶ 短暂空档 ──▶ GPU 满载（embedding）──▶ CPU 再上（建库）
     几小时                              几十分钟                   几十秒
```

### 4.3 embedding 从生产主机搬到算力节点

```
第一版：在生产主机上跑 embedding
  → 6 GB 显存的上一代 GPU
  → 速度约为算力节点的 1/4 到 1/6

第二版：改由算力节点跑
  → 8 GB 显存的移动版 GPU
  → 402,638 块，快 4-6 倍

⇒ 教训：embedding 是整条流水线里 GPU 收益最大的环节，
        值得为它单独调度一台机器
```

## 五、P50 / P95 是什么

一句话：

```
把 100 次查询的耗时按从小到大排好队

P50 = 第 50 名的耗时  → 一半的查询比它快，一半比它慢
                        「典型体验」
P95 = 第 95 名的耗时  → 只有 5% 的查询比它慢
                        「坏情况有多坏」
```

**⇒ 为什么不能只看平均值：**

```
平均值会被极快和极慢的样本互相抵消
⇒ 掩盖了「偶尔卡一下」的真实体验

P95 更能反映用户感受：
  如果 P95 是 800 ms，哪怕平均值只有 150 ms，
  用户仍然每 20 次就有一次要等接近 1 秒
```

**⇒ 本次实测（60 次串行）：**

```
服务端 P95   135 ms
最大          158 ms
⇒ 超过 200 ms 的一次都没有
```

**⇒ 为什么必须串行测：**

```
并发测延迟会争用模型锁，测出 211 ms
⇒ 误判为超时
⇒ 所有性能数据必须串行跑
```

## 六、调试：三个真问题

### 6.1 去噪

```
症状：查什么都返回一堆无关文件
原因：向量通道会「觉得」某些内容语义相近，
      把不相关的东西也拉进来

做法：
  · 加最小分数阈值
  · 短查询词（BBU / 型号 / 日期）不走向量主导
  · 用文件通道兜住「确定性」的那部分
```

### 6.2 权重调整（这一节是重点）

**症状：**

```
查一个设备缩写（3 个字母）→ 返回全是不相关的实施方案
查同一个词直接怼数据库 → 10 条精准命中

⇒ 不是没数据，是被埋了
```

**根因分析：**

```
每个通道都取几百条候选
⇒ 正文章节体量大，吐出上千条
⇒ 文件通道只有几十条
⇒ RRF 投票时，文件结果被压到第 49 名之后
```

**三种解法：**

```
① 提高文件通道权重
   → 简单，但权重再高也拼不过数量优势

② 缩小分母：文件意图查询时，正文只取 20 条
   → 有效

③ 意图分流：不同查询走不同策略
   → 最彻底
```

**最终用了 ② + ③。**

**意图识别规则：**

```
判为「文件意图」：
  含扩展名 / 路径分隔符
  含设备型号（忽略 - _ . 空格）
  含日期（2011.11.23 等）
  含 8 位以上工单号
  含设备缩写（大写字母 2-8 位）
  且词数 ≤ 3

但必须抑制：
  含「内容 / 查询 / 如何 / 怎么 / 介绍 / 说明 / 原理 / 配置 / 故障 / 方案」
  ⇒ 判为语义查询，不走文件模式
```

**动态权重表：**

| 通道 | 语义查询 | 文件意图 |
|---|---:|---:|
| 文件名/路径精确 | 3.0 | **10.0** |
| 完整文件名匹配 | 3.0 | **9.0** |
| 型号/缩写/日期/工单号 | — | **8.0** |
| 其他文件 FTS | 0.7 | **5.0** |
| 元数据 | 2.5 | 2.5 |
| 正文 / 向量 | 1.0 | 1.0 |

**候选集收窄：**

```
语义查询：正文/向量各 500 条，文件 500 条
文件意图：正文/向量各 20 条，文件 50-100 条
```

**效果：**

```
改前：查设备缩写 → 前 3 条全是无关方案
改后：查设备缩写 → 前 3 条全部精准
      语义查询（自然语言长句）→ 完全没退化
延迟：P95 135 ms，仍在 200 ms 内
```

**⇒ 核心心法：**

```
不是「让对的答案分数更高」
而是「让错的答案没机会进候选池」
```

### 6.3 三个顺手修的边界

```
① 型号分隔符不一致
   查询写 <型号>，文件名写 <型号> → 匹配不上
   修法：匹配时忽略 - _ . 空格

② 裸扩展名查询
   查「ISO」→ 返回源码文件 iso2022jp.go
   修法：识别裸扩展名时优先按扩展名过滤

③ 重复路径占位
   同一文件在两个库里都有，占掉两个位次
   修法：文件意图时只取文件目录库
```

## 七、成本：296 元买到的认知

**⇒ 26 天，五个 API key，总计 296.59 元。**

```
按 key 分：
  生产主机 agent   139.34  (47%)
  控制台 agent      92.67  (31%)
  文档 agent        58.52  (20%)
  本地支援 agent     5.24  (2%)
  测试               0.82

按阶段分：
  需求沟通期（周五之前）  大量对话，费用分散
  干活期（周六-周日）     单日最高 38 元
  收尾期（周一）          17.86 元
```

**⇒ 一个重要的反直觉发现：**

```
原本以为：本地执行不烧 token，只有出问题才回问
实测：本地执行期间，单日仍花 24.92 元，占当天 86%

原因：agent 在本地跑循环，每一步都要模型判断
      「下一步做什么」「这个结果对不对」
      ⇒ 本地执行 ≠ 零成本
```

**⇒ 真正省钱的是什么：**

```
缓存命中率 98.5% - 99.1%
输入总量：生产主机 2,694M + 控制台 2,332M + 文档 1,136M
⇒ 输入量巨大，但 98.5% 走缓存价（约 1/50）

如果没有缓存，同样的活要花 10 倍以上
```

**⇒ 结论：**

```
省 token 的第一原则不是「少调用」
而是「让上下文尽量稳定、可命中缓存」
```

## 八、可复用的方法论

### 8.1 分工原则

```
生产主机 = 仓库 + 常驻服务   （必须 24×7，最弱也没关系）
算力节点 = 批量计算         （按需上岗，最强但可以不在）
控制台   = 协调 + 判断       （最弱，但必须在）
```

**⇒ 别把三件事压在一台机器上。**

### 8.2 索引不能离开数据

```
FTS5、向量、embedding 模型版本
⇒ 必须同居一台机器

原因：模型换了，向量就作废
      切块策略变了，chunk_id 就对不上
```

### 8.3 一次性快照，不做双向同步

```
语料打包 → 算力节点 → 处理 → 结果回传
每条记录 exit_code，写 status.json
不用 /MIR（会删对端）

⇒ 慢一点，但不会两边互相污染
```

### 8.4 验收必须留痕

```
每个阶段都要有：
  · 输入文件数、字节数
  · 输出块数、字符数
  · 结构校验（块数 = ID 数，向量行序对齐）
  · 哈希校验（关键文件 SHA-256）
  · 性能基准（P50 / P95，串行）

⇒ 「跑完了」不是结论，「校验通过」才是
```

### 8.5 agent 协作的铁律

```
传「需求」，不传「动作」
  · 写需求单 → 对端读 → 自己做 → 自己回执
  · 不用 scp 塞文件，不用远程执行二进制

原因：对端 agent 有判断力，
      你告诉它「要什么」，比告诉它「怎么做」更可靠
```

## 八点五、过程中会产生哪些文件

**⇒ 这套流程基本不产代码，产的是「数据中间件」和「证据」。**

**⇒ 按阶段列，括号里是它起什么作用：**

### 阶段 1：扫描与去重

```
manifest.json          （输入清单：文件数、字节数、来源根、扫描时间）
files_ruled.csv        （逐文件裁决：解析成功 / 需 OCR / 不支持 / 敏感跳过）
dedupe_report.json     （去重结果：重复数、保留数、SHA-256 对照）
```

### 阶段 2：抽取与切块

```
documents.jsonl        （每份文档一行：路径、类型、字符数、抽取状态）
chunks.jsonl           （每块一行：chunk_id、doc_id、正文、起止偏移）
chunk_ids.json         （块 ID 索引：与 chunks.jsonl 行序一一对齐）
```

### 阶段 3：向量化

```
vectors.f16.npy        （向量矩阵：N×512，float16，行序与 chunk_ids 一致）
vector_meta.json       （指纹：模型名、revision、维度、归一化方式）
```

### 阶段 4：建库

```
kb.sqlite3             （主库：FTS5 倒排 + 元数据表 + 块表）
catalog.sqlite3        （文件目录库：只存路径、大小、时间、扩展名）
```

### 阶段 5：验收

```
INDEX_COMPLETE.json    （建库完成标记：块数、文档数、耗时、版本）
acceptance_verify.json （验收结果：结构校验、哈希校验、样本查询命中）
benchmark_results.json （性能基准：P50 / P95 / 最大值）
status.json            （分阶段 exit_code，供失败重跑定位）
```

**⇒ 这些文件的分工很清楚：**

```
清单类     证明「扫了什么」          manifest / files_ruled
内容类     存正文和块                chunks / documents
索引类     能查的                    kb.sqlite3 / catalog.sqlite3
指纹类     证明「是哪一版」          vector_meta / INDEX_COMPLETE
验收类     证明「跑对了」            acceptance_verify / benchmark
```

**⇒ 一条纪律：每个阶段都必须留下「输入数、输出数、耗时」三件套。**

```
没有这三个数的阶段，等于没跑过
⇒ 出了问题无法定位是「没读到」还是「读了没写」
```

## 九、这次没做、但知道该做的

```
· 没接本地大模型（现在只做检索，生成还是调云端）
· 没做重排（rerank），只做了 RRF 融合
· 没做增量索引（现在是全量重建）
· 没做权限隔离（都是自己的资料）
· 没做对象存储（用过目录 + SQLite 替代）
· 图表卡片的自动提炼（现在靠人工）
```

**⇒ 每一条都是下一步的入口，不是缺陷。**

## 十、一句话总结

```
用自己桌上的三台机器，把「算力按需调度」这件事
走了一遍完整的物理流程：

  数据搬过去 → 算完 → 结果搬回来

大厂用旗舰 GPU 和光纤做的事，我们用一根网线和一台笔记本做了一遍。
框架、软件、硬件、成本，四面都趟过。

最大的收获不是知识库本身，
而是知道了：
  什么时候 CPU 满载是对的
  什么时候 GPU 才真正值钱
  什么时候该换路子，而不是继续调参数
```
