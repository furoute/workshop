# 自建知识库：从一堆 Office 文件到可查可点的知识库

> 2026-10-24（1024 程序员节）
> 面向智能体读者：这是一套可照做的框架，不止给人看的报告。

![自建知识库架构图](assets/kb-architecture.svg)

> **本文档是一次完整实践的全记录**：从零到可查，从只有关键词到双路检索，
> 从一台机器到三台机器分工。按章节写，智能体照做即可。

## 一、先想清楚：FTS5 和 RAG 不是二选一

**v1.0 的时候，我们只上了 FTS5，理由是「轻量」。**
**v2.0 改口了：两条腿走路，缺一条就瘸。**

### 1.1 两条腿分别擅长什么

| 维度 | FTS5（关键词） | 向量（语义） |
|---|---|---|
| 索引方式 | 倒排表，字面精确命中 | 向量化，语义近似 |
| 依赖 | SQLite 内置，零外部服务 | embedding 模型 + 向量数组 |
| 快不快 | 毫秒级 | 十几到几十毫秒 |
| 精确匹配（型号、编号、金额、日期） | ✅ 强 | ❌ 弱，易漏 |
| 语义模糊（"这个事怎么办"） | ❌ 弱 | ✅ 强 |
| 可解释 | ✅ 命中哪个文件哪一段 | ❌ 黑箱 |
| 资源 | 极低 | 要 GPU 才划算 |

**⇒ 结论：**

```
问「是什么」      → FTS5
问「怎么办、类似的有哪些」→ 向量
```

### 1.2 怎么合起来：RRF

**⇒ 两路各出候选，按「名次」投票，不看原始分数。**

```
为什么不直接加权求和原始分数？
  FTS5 的 bm25 分数和向量的余弦相似度
  量纲不一样，加起来没意义

RRF 只看名次：
  score = Σ 1 / (k + rank)
  ⇒ 两路都排得靠前的，融合后最靠前
  ⇒ 一路命中一路没命中的，也能进候选
```

**⇒ 这是「两条腿」真正合起来的地方。**

### 1.3 代价

```
· 多一份 embedding 的存储（N×512 float16）
· 多一次模型推理（查询时要编码）
· 多一个向量加载（常驻内存）
· 建库时间变长（GPU 才能压住）

⇒ 换来的是：语义查询从「查不到」变成「查得到」
```

## 二、整体架构：四层数据 + 一层算力

```
┌─────────────────────────────────────┐
│  展示层  Obsidian + LLM Wiki         │  ← 给人看
│  卡片 / 主题 / 决策 / 问答 / 关系图    │
├─────────────────────────────────────┤
│  判断层  人工结论 + 证据绑定           │  ← 人负责
├─────────────────────────────────────┤
│  证据层  SQLite：FTS5 + 向量 + RRF    │  ← 给智能体查
│  倒排索引 / 向量数组 / SHA-256 / 溯源  │
├─────────────────────────────────────┤
│  事实源  原文件（原位只读，绝不搬动）    │
└─────────────────────────────────────┘

        ┌── 算力层（横切）──┐
        │ 控制台：协调/分发   │
        │ 生产主机：仓库/服务 │
        │ 算力节点：批量计算  │
        └──────────────────┘
```

**⇒ 索引放 SSD，语料放 HDD——这一条比选什么框架更重要。**

```
FTS5 是随机读密集
机械盘上每次查询等磁头
固态盘上直接命中页缓存
⇒ 语料几 TB 便宜地放着，索引几百 MB 放在贵的地方
```

**⚠️ 最重要的一句话：**

> **Obsidian 和 LLM Wiki 只是展示层。真正的实际意义在 FTS5。**
> 智能体去读、去找，靠的是 FTS5；Obsidian 的 Wiki 是给人看的关系图和摘要。
> 而且很多时候并不方便——Office 文件点不开就只剩一个文件名。
> **别让展示层喧宾夺主。**

## 四、七步流程

### 第 1 步：全量探针（只读）

```
· 全量清单：路径、文件名、大小、mtime、扩展名
· 只读首尾 64 字节判魔数，不解析正文
· 四类分诊：正常 / 格式伪装 / 损坏 / 加密占用
```

**为什么先做这步**：不摸清家底就动手，后面全是返工。

**典型发现**：
```
· 201 个文件扩展名是 .doc，实际是 HTML
· 7,122 个文件从 NAS 同步损坏，无文本层
· 6 个 PDF 是「权限加密」不是真加密，空密码就能开
```

### 第 2 步：SHA-256 去重（只读）

```
· 只对「正常」文件算哈希（跳过伪装/损坏）
· 完全重复 → 合并组，每组留一个代表
· 版本族只聚类，不判最新
```

**铁律：精确重复只认 SHA-256。** 同名不代表同意，同大小也不代表同意。

**实测**：某个目录 291 个重复组、719 个文件，可省 3.89 GB。

### 第 3 步：分层抽样试读（只读）

```
· 按「目录 × 年代 × 大小」分层抽 400-500 个
· 旧 .doc 先魔数嗅探挑假 doc，再试跑 100 个
· 只读校验：试读前后全量重算 SHA，必须 0 变化
```

**这步的关键是「证明自己没改文件」。** 用 Office COM 打开 .xls 会写回元数据，SHA 会变——所以要复制到临时目录再读。

### 第 4 步：自动分诊三堆（只标注）

```
A 确定有用   B 确定垃圾   C 待定（按文件族聚合）
```

**C 堆必须按「文件族」聚合**，几万个待定列成行没人看得下去，聚成几十族才行。

**典型 B 堆**：`~$` 锁文件、`.DS_Store`、0 字节空文件、下载失败的占位文件、16 字节的临时脚本。

### 第 5 步：批量裁决（只标注）

套 28 条规则，每族给终态 `keep / keep_index / delete / needs_review`。

**核心几条：**
```
D01  同名多版本     → 文件名日期留最新，其余只留索引
D21  旧版/备份/副本  → 人审，不自动判垃圾
D26  精确重复       → 只认 SHA-256
D27  无法确定归属    → 人审
```

### 第 6 步：建实体卡

**五类实体**：项目 / 方案 / 机会 / 规范 / 采购
**十五个 YAML 字段 + 九段正文**

**两个铁律：**

**铁律 1 — 证据分级不能抬**
```
strong          有中标公告 / 成交通知书 / 合同
directory-only  只有目录名 / 文件名
unknown         推断
```
「待核」只能用于事实判断（客户是谁、多少钱），不能用于证据等级。没读到就不能抬级。

**铁律 2 — 金额口径写死**
```
有金额：本金额为 XX（预算/限价/报价/成交/合同），不可与其他数字相加
无金额：未采信任何金额
```
不做口径标注的金额，后续一定会被跨卡相加，得出错误总数。

### 第 7 步：呈现层（可选，给人看）

```
index.md + 属性视图 + 主题页 + 决策页 + 问答页
```

**这一步是给人看的，不是给智能体看的。** 智能体用 FTS5 就够了。

## 五、RAG 落地：四步流水线

**⇒ 切块、向量、融合，一步都不能省，但顺序不能乱。**

### 第 1 步：抽取

```
PDF / Office / 扫描件
  → 文本层能读就读
  → 扫描件走 OCR（CPU 密集）
  → 加密就跳过，不硬啃

输出：每份文档一行（路径、类型、字符数、状态）
```

**⇒ 这一步 100% 吃 CPU，GPU 一点忙都帮不上。**

```
实测：24 核跑满，GPU 占用 0%，温度功耗不动
原因：文本解析是 I/O + 字符串处理，没有矩阵运算
```

### 第 2 步：切块

```
400 字一块，重叠 50 字
⇒ 既不让一块太长（语义稀释）
⇒ 又不让上下文断掉（重叠兜住边界）
```

**⇒ 切块策略必须固定并记录版本。**

```
块数和 chunk_id 严格 1:1
否则向量和正文对不上，检索结果全错位
```

### 第 3 步：向量化

```
512 维，float16 存储
批量推理，GPU 才划算

实测：
  上一代中端显卡  → 慢
  移动版新卡      → 快 4-6 倍
⇒ embedding 是整条流水线里 GPU 收益最大的环节
```

**⇒ 指纹必须固定：模型名 + revision + 维度 + 归一化方式。**

```
模型一换，所有向量作废
⇒ 换模型 = 全量重建，没有捷径
```

### 第 4 步：融合（RRF）

```
FTS5 出 N 条候选（按 bm25 排序）
向量出 N 条候选（按余弦排序）
RRF 按名次投票融合
⇒ 出最终 top_k
```

**⇒ 这四步的顺序不能换：先有块，才有向量；先有向量，才能融合。**

## 六、降噪规则（一条条列）

### 一律删除，无需人审

```
iso img vhd vhdx ova ovf vmdk qcow2    虚拟化镜像
exe msi msix appx                      Windows 安装包
deb rpm pkg dmg                        Linux/macOS 安装包
apk ipa                                移动端安装包
so dll sys ocx a lib                   动态库 / 驱动
```

**例外保留**：业务 APP 的 apk、便携工具、项目配置盘（.vdi）。

### 系统垃圾

```
~$ 开头的 Office 锁文件
.~ 开头的临时占位文件
.DS_Store / ._ 开头的 macOS 残留
.download 结尾的下载失败文件
0 字节空文件（先确认是否补件）
```

### 特殊标注必须保留

```
（内部）/（客户侧）            不同受众，都留
（模板）/（OCR）              不同类型，都留
附件1 / 附件2                 不同附件，都留
优化服务 / 运维服务 / 运维及优化服务   不同业务，都留
```

**这是最容易误删的一类。** 名字像版本，实际是不同业务对象。

### 按月资料不是版本

```
月报、月度统计，文件名只差日期
⇒ 整族保护，不参与版本比较
```

### 扫描件不能一刀切

```
有文本层                              → 正常抽取
无文本 + 命中「中标/成交/合同/通知书/结果」 → 渲染 1-2 页关键页
无文本 + 不命中                        → 判 directory-only
```

**理由**：中标通知书、成交通知书常常是扫描件，一刀切会把 strong 证据降成目录依据。

### 大目录（500+ 实体）分层建卡

```
score = 文件数 + 3 × 证据数
TOP 30%  → 建主卡（card_tier: main）
后 70%   → 只写总索引一行，不建卡但不消失
已有卡   → 标 card_tier: archive，不推倒重来
```

**金额不要进公式**——金额藏在正文里，覆盖不全。

## 七、检索调优：让错答案没机会进候选池

**⇒ 这是整件事里最反直觉的一课。**

### 症状

```
查一个设备缩写（3-5 个字母）
→ 返回全是不相关的实施方案
→ 但直接怼数据库 FTS5，10 条精准命中

⇒ 不是没数据，是被埋了
```

### 根因

```
每个通道都取几百条候选
⇒ 正文章节体量大，吐出上千条
⇒ 文件通道只有几十条
⇒ 融合时文件结果被压到第 49 名之后
```

### 三种解法

```
① 提高文件通道权重
   → 简单，但权重再高也拼不过数量优势

② 缩小分母：文件意图查询时，正文只取 20 条
   → 有效

③ 意图分流：不同查询走不同策略
   → 最彻底

⇒ 最终用 ② + ③
```

### 意图识别

```
判为「文件意图」：
  · 含扩展名 / 路径分隔符
  · 含设备型号（忽略 - _ . 空格）
  · 含日期（2011.11.23）
  · 含 8 位以上工单号
  · 含大写缩写（2-8 位）
  · 且词数 ≤ 3

必须抑制：
  · 含「内容 / 查询 / 如何 / 怎么 / 介绍 / 说明 / 原理 / 配置 / 故障 / 方案」
  ⇒ 判为语义查询，不走文件模式
```

### 动态权重

| 通道 | 语义查询 | 文件意图 |
|---|---:|---:|
| 文件名/路径精确 | 3.0 | 10.0 |
| 完整文件名匹配 | 3.0 | 9.0 |
| 型号/缩写/日期/工单号 | — | 8.0 |
| 其他文件 FTS | 0.7 | 5.0 |
| 元数据 | 2.5 | 2.5 |
| 正文 / 向量 | 1.0 | 1.0 |

**⇒ 正文和向量的权重一点没动——这是语义查询不退化的前提。**

### 候选集收窄（关键）

```
语义查询：正文/向量各 500 条，文件 500 条
文件意图：正文/向量各 20 条，文件 50-100 条
```

### 心法

> **不是「让对的答案分数更高」**
> **而是「让错的答案没机会进候选池」**

### 调优纪律

```
① 改前先记录语义查询的排序
② 改后再跑一遍，对比
③ 确认「没退化」才算成功
④ 性能必须串行测（并发会争用模型锁，误判超时）
```

## 八、让 Obsidian 能点开原件

**不做这一步，知识库就只有文件名，什么都点不开。**

Markdown 只能链 `.md`，链不到 doc/pdf/xls。解法是 `file:///` 外链。

### 关键：链接必须写在正文，不能写在 YAML

```markdown
### 来源链接

| 标记 | doc_id | 文件 | SHA-256 |
|---|---|---|---|
| 主体 | SRC-c1b10ca7 | 📕 [某某中标通知书.pdf](file:///<盘符>/<URL编码后的路径>) | c1b10... |
```

**YAML frontmatter 里的 Markdown 永远不渲染**，写进去只显示原始字符串。

### 路径必须 URL 编码

```python
from urllib.parse import quote
uri = "file://" + quote(path.replace("\\", "/"), safe="/:")
```

中文、空格、`(` `)` 全部要编码——`(` `)` 不编码会直接打断 Markdown 链接语法。

### 验证

```
① 切到阅读视图（Ctrl+E）才看得到蓝色链接
② 路径全部存在（生成前 os.path.exists 过一遍）
③ 改完链接数 = 来源数
```

**⚠️ 建卡时就要把相对路径写进 sources**，否则后期加不了链接。

## 九、Obsidian 在 Windows 上的安装

```
① 下载：https://obsidian.md → Download for Windows
② 安装：默认选项即可，装到用户目录
③ 首次启动：选择「打开本地文件夹作为 vault」，指向知识库 vault 目录
④ 命令行（可选，给智能体用）：
   设置 → 通用 → 命令行界面（CLI）→ 启用
   或把 Obsidian 安装目录加入系统 PATH
⑤ 配置外部链接：
   设置 → 文件与链接 → 外部链接 → 用默认程序打开
```

**CLI 常用：**
```powershell
obsidian vault=<vault名> files total
obsidian vault=<vault名> read file=<笔记名>
obsidian vault=<vault名> backlinks file=<笔记名> total
obsidian vault=<vault名> unresolved verbose
```

**中文输出会乱码**，要落文件 + `chcp 65001` + base64 回传。

## 十、踩过的坑（照抄就行）

| 坑 | 现象 | 解法 |
|---|---|---|
| Excel COM 写回元数据 | 读 .xls 后 SHA 变 | 复制到临时目录再读，或用 xlrd/pandas |
| 双链正则误报断链 | 报 59% 断链，实际 0 | 非贪婪 `+?` + 单独吃 `\\?`，只比文件名 |
| CLI 不认未注册 vault | `Vault not found` | 改 obsidian.json 加 key + 重启 Obsidian |
| 链接写在 YAML | 永远不渲染 | 挪到正文 `## 来源` 表格里 |
| 中文没 URL 编码 | 链接断 | `quote(path, safe="/:")` |
| 打开备份目录验证 | 看起来像没改成功 | 确认路径是真正的 vault |
| 源码视图 | 链接不渲染 | Ctrl+E 切阅读视图 |
| 只读属性挡删除 | WinError 5 | `os.chmod(path, stat.S_IWRITE)` |
| 唤醒进程随 SSH 断连被杀 | 输出文件不存在 | `schtasks /create /sc once` + `/run` |
| 按月资料被当版本删 | 29 个月报只留 1 个 | 整族保护 |

---

### 本次新增的坑

```
① 索引放机械盘
   → 热查询有几百毫秒抖动
   → 挪到固态盘，稳定 100 ms 级
   ⇒ 别因为「盘大」就把索引放过

② 所有通道取一样多的候选
   → 正文候选淹没文件候选
   ⇒ 短查询词必须收窄正文候选

③ 并发测延迟
   → 争用模型锁，测出 211 ms，误判超时
   ⇒ 性能数据一律串行跑

④ 型号分隔符不一致
   → 写 <型号>，文件叫 <型号>，匹配不上
   ⇒ 型号匹配要忽略 - _ . 空格

⑤ 裸扩展名查询
   → 查「ISO」返回源码文件 iso2022jp.go
   ⇒ 裸扩展名优先按扩展名过滤

⑥ 同一文件在两个库都有
   → 占掉两个推荐位次
   ⇒ 文件意图查询时只取文件目录库

⑦ embedding 换模型不重建
   → 向量和正文对不上，检索全错位
   ⇒ 换模型 = 全量重建，没有捷径
```

## 十一、实践记录：三台机器跑一遍

**⇒ 上面是「怎么做」，这一节是「实际怎么跑通的」。**

### 11.1 为什么不用一台机器

```
生产主机：开着就挂查询服务，但不开机能省电、也能躲开占用
算力节点：批量计算时 CPU 24 核全满，会把同一台机器上的服务拖死
控制台：只做协调，不碰重活
```

**⇒ 三台机器，三种角色，按需上岗，互不干扰。**

**⇒ 关键不是「谁常开」，而是「谁随时能接管」。**

| 角色 | CPU | 内存 | GPU | 存储 | 状态 |
|---|---|---|---|---|---|
| 生产主机 | 6 核 12 线程 | 32 GB | 6 GB 独显 | SSD 465 GB（索引）+ HDD 1.8 TB | **按需开机** |
| 算力节点 | 24 核 32 线程 | 32 GB DDR5 | 8 GB 显存 | NVMe 1 TB | 插电 + 网线才上岗 |
| 控制台 | 4 核 | 8 GB | 无 | 小容量 | 常开（最省电） |

**⇒ 为什么生产主机不必 7×24：**

```
· 它是自己的机器，不是机房设备
· 不用的时候关掉：省电、省磨损、少噪音
· 查询服务「用的时候再起」，冷启动约 1.1 秒
  · 模型常驻后热查询 60-90 ms
  · 冷启动那一次一秒多，可以接受

⇒ 真正要 7×24 的只有一样东西：数据不能丢
   原文件在盘上，索引在 SSD 上
   机器关着，数据也在
⇒ 可靠的是资产，不是机器
```

### 11.2 索引放 SSD，比什么都重要

```
数据盘（机械）  语料放这里，几十 GB，不用动
系统盘（固态）  索引放这里：SQLite + FTS5 + 向量

FTS5 是随机读密集
机械盘上每次查询等磁头寻道
固态盘上直接命中页缓存

⇒ 索引在机械盘：几百毫秒抖动
   索引在固态盘：稳定 100 ms 级
```

**⇒ 别因为「盘大」就把索引放过——这是最常见的一次性错误。**

### 11.3 CPU 满载 vs GPU 上岗

**⇒ 这是被监控数据逼出来的认知。**

| 阶段 | CPU | GPU | 原因 |
|---|---|---|---|
| 抽取（PDF/Office/OCR） | 24 核全满 | 0%，温度不动 | 文本解析是 I/O + 字符串，无矩阵运算 |
| 切块 | 中等 | 0% | CPU 够用 |
| **向量化** | 低 | **满载** | 矩阵运算，GPU 收益最大 |
| 建库（FTS5） | 短暂满载 | 0% | 倒排构建，CPU 活 |

**⇒ 流水线形态：**

```
CPU 满载几小时（抽取）
  → 短暂空档
  → GPU 满载几十分钟（向量化）
  → CPU 再上几十秒（建库）
```

**⇒ 向量化从生产主机搬到算力节点：**

```
6 GB 显存（上一代）→ 8 GB 显存（新一代）
实测快 4-6 倍

⇒ GPU 收益最大的环节，值得单独调度一台机器
```

### 11.4 两条路并行

```
路 1  本地 RAG（切块 + embedding + FTS5 + RRF）
路 2  整段任务交给算力节点（数据过去、算完、回来）
```

**⇒ 路 2 的本质就是「按需租用算力」，只不过租的是自己桌上那台。**

```
大厂：顶级加速卡 / 光纤 / RDMA
我们：一台笔记本 + 一根千兆网线
原理相同：数据过去 → 算完 → 结果回来
```

### 11.5 通信方式

```
控制台 → 生产主机/算力节点   ACP 信箱 + SSH 唤醒（间歇）
生产主机 ↔ 算力节点          千兆网线 / 一次性快照
控制台 → 查询服务            HTTP 常驻
控制台 ↔ 生产主机            文件同步（常驻）
```

**⇒ 一条铁律：**

```
传「需求」，不传「动作」

❌ 不用 scp 塞文件、不用远程执行二进制
✅ 写需求单 → 对端 agent 读 → 自己做 → 自己回执
```

**⇒ 因为 agent 有判断力，告诉它「要什么」比「怎么做」更可靠。**

### 11.6 过程中会产生哪些文件

**⇒ 这套流程基本不产代码，产的是「数据中间件」和「证据」。**

| 阶段 | 文件 | 作用 |
|---|---|---|
| 扫描去重 | `manifest.json` | 输入清单：文件数、字节数、来源根、扫描时间 |
| | `files_ruled.csv` | 逐文件裁决：解析成功 / 需 OCR / 不支持 / 敏感跳过 |
| | `dedupe_report.json` | 去重结果：重复数、保留数、SHA-256 对照 |
| 抽取切块 | `documents.jsonl` | 每份文档一行：路径、类型、字符数、抽取状态 |
| | `chunks.jsonl` | 每块一行：chunk_id、doc_id、正文、起止偏移 |
| | `chunk_ids.json` | 块 ID 索引，与 chunks.jsonl 行序一一对齐 |
| 向量化 | `vectors.f16.npy` | 向量矩阵 N×512，float16，行序与 chunk_ids 一致 |
| | `vector_meta.json` | 指纹：模型名、revision、维度、归一化方式 |
| 建库 | `kb.sqlite3` | 主库：FTS5 倒排 + 元数据表 + 块表 |
| | `catalog.sqlite3` | 文件目录库：路径、大小、时间、扩展名 |
| 验收 | `INDEX_COMPLETE.json` | 建库完成标记：块数、文档数、耗时、版本 |
| | `acceptance_verify.json` | 验收：结构校验、哈希校验、样本命中 |
| | `benchmark_results.json` | 性能基准：P50 / P95 / 最大值 |
| | `status.json` | 分阶段 exit_code，供失败重跑定位 |

**⇒ 一条纪律：每个阶段都必须留下「输入数、输出数、耗时」三件套。**

```
没有这三个数的阶段，等于没跑过
⇒ 出了问题无法定位是「没读到」还是「读了没写」
```

### 11.7 验收必须留痕

```
· 输入文件数、字节数
· 输出块数、字符数
· 结构校验（块数 = ID 数，向量行序对齐）
· 哈希校验（关键文件 SHA-256）
· 性能基准（P50 / P95，串行跑）
```

**⇒ 「跑完了」不是结论，「校验通过」才是。**

### 11.8 这次没做、但知道该做的

```
· 本地大模型（现在只做检索，生成还是调云端）
· 重排（rerank），只做了 RRF 融合
· 增量索引（现在是全量重建）
· 权限隔离
· 对象存储（用目录 + SQLite 替代）
· 卡片自动提炼
```

**⇒ 每一条都是下一步的入口，不是缺陷。**

## 十二、P50 / P95 是什么

一句话：

```
把 100 次查询的耗时按从小到大排好队

P50 = 第 50 名 → 一半比它快，一半比它慢 → 典型体验
P95 = 第 95 名 → 只有 5% 比它慢 → 坏情况有多坏
```

**⇒ 为什么不能只看平均值：**

```
平均值会被极快和极慢的样本互相抵消
⇒ 掩盖了「偶尔卡一下」的真实体验

P95 才反映用户感受：
  P95 = 800 ms 时，哪怕平均只有 150 ms，
  用户仍每 20 次就有一次要等接近 1 秒
```

**⇒ 本次实测（60 次串行）：服务端 P95 = 135 ms，最大 158 ms，全部在 200 ms 内。**

**⇒ 必须串行测：并发会争用模型锁，测出 211 ms，误判超时。**

## 十三、性能实测

**⇒ 环境：生产主机（6 核 12 线程 / 32 GB / 系统盘 SSD）**

### 总体结果

| 指标 | 数值 |
|---|---|
| 冷启动（模型加载） | 1,121 ms |
| 服务端 p50 | **61.2 ms** |
| 服务端 p95 | **71.5 ms** |
| 客户端 p50（含 HTTP） | 66.6 ms |
| 客户端 p95（含 HTTP） | 91.1 ms |

**⇒ 端到端 p95 91 ms，远低于 200 ms 目标。**

### 分阶段耗时

| 阶段 | p50 | p95 | 目标 | 结论 |
|---|---:|---:|---:|---|
| 查询编码（512 维，CPU） | 5.94 ms | 7.33 ms | <50 ms | ✅ |
| FTS5 全文检索 | 6.63 ms | 19.84 ms | <20 ms | ✅ |
| 向量检索（55 万块暴力算） | 45.53 ms | 46.56 ms | <80 ms | ✅ |
| RRF 融合排序 | 2.01 ms | 2.82 ms | <10 ms | ✅ |
| 结果组装 | ~0.9 ms | — | — | ✅ |

**⇒ 向量检索是主要成本（约 45 ms），因为对全量向量做精确搜索，不是近似索引。**

### 索引规模

| 数据集 | 数据库 | 向量 | chunks |
|---|---:|---:|---:|
| 主库 | 950 MB | 412 MB | 402,638 |
| 补充库 | 316 MB | 149 MB | 153,926 |
| 文件目录库 | 5 MB | — | 3,932 条 |

**合计索引 1.83 GB，全部在 SSD 上。**

### 为什么能做到 60-90 ms

```
① 模型常驻（只加载一次，省 1-8 秒）
② 向量一次读进内存（561 MB，32 GB 内存充裕）
③ FTS5 连接常开（不每次重连）
④ 查询编码 batch=1（不做过度批处理）
```

### 向量检索为什么是 45 ms

```
对全量向量做精确余弦相似度
55 万条 × 512 维 float16
⇒ NumPy 矩阵运算，一次约 45 ms
⇒ 没用 ANN 索引（HNSW/IVF），是精确解，无近似误差
```

**⇒ 这个规模下暴力搜索完全够用，不需要引入向量数据库。**

### 与云端方案对比

| 维度 | 本地方案 | 云端 API |
|---|---|---|
| 单次查询延迟 | 60-90 ms | 300-1500 ms |
| 单次成本 | ~0（电费） | 有按次计费 |
| 数据出网 | 不出 | 全部出网 |
| 断网可用 | 是 | 否 |
| 规模上限 | 内存（32 GB 约 600 万条） | 无限但要付费 |
| 模型升级 | 手动换 + 重建 | 换 API 版本即可 |

### 局限

```
· 补充库只有 130 份样张正文（正文补库没跑完）
· 向量是暴力计算，300 万条以上会明显变慢
· 单机服务，没有并发压测
```

## 十四、给智能体的用法

**这套东西的目的是：让智能体照框架做，少写提示词。**

```
1. 先读本文档
2. 按七步走，每步产出落文件
3. 每步做完给数字（文件数 / 大小 / 分诊结果）
4. 判不了的进 C 堆 / needs_review，不许硬猜
5. 删除等用户点头，标注不删除
```

**查询侧：**
```
· 精确问题（型号/编号/金额/日期）→ 走文件意图，FTS5 主导
· 模糊问题（怎么办/类似的有哪些）→ 走向量语义
· 两路都会出候选，RRF 融合后给结果
· 要摘要和关系                  → 看卡片
· 要看原文                      → 点 file:/// 链接
```
