# 自建知识库：从一堆 Office 文件到可查可点

> 面向智能体读者：这是一套可照做的框架，不是给人看的报告。
> 术语第一次出现时用括号补一句，后面不再解释。

![自建知识库架构图](assets/kb-architecture.svg)

## 一、这个项目到底在干什么

不是"把每个字挖出来"，是**用智能体跑通一条完整的本地 RAG 链路**：几十 GB 乱七八糟的
Office/PDF → 清点、去重、分诊 → 抽正文、切块、向量化 → 双路检索 → 模型作答 → 能点回原件。

两条腿走路，缺一条就瘸：

| | FTS5（关键词） | 向量（语义） |
|---|---|---|
| 擅长 | 型号、编号、金额、日期，字面精确 | "这个事怎么办"这类模糊问法 |
| 弱在 | 换个说法就查不到 | 精确串易漏，黑箱不可解释 |
| 成本 | SQLite 内置，零外部服务，毫秒级 | 要 embedding 模型 + GPU 才划算 |

```
FTS5 —— SQLite 的全文检索模块，按词建倒排索引
向量 —— 把一段文字压成一串数字，用来算相似度
RRF  —— 把两路检索结果按"名次"合并的算法，score = Σ 1/(k+rank)
```

**为什么不加权求和原始分数**：FTS5 的 bm25 分和余弦相似度量纲不同，加一起没意义。
只看名次：两路都靠前的融合后最靠前，一路命中一路没命中的也能进候选。

代价：多一份向量存储、多一次查询编码、多一个常驻向量数组、建库更慢；换来语义查询从"查不到"变"查得到"。

## 二、架构：四层数据 + 一层算力

```
展示层   Obsidian + LLM Wiki          ← 给人看
判断层   人工结论 + 证据绑定            ← 人负责
检索层   SQLite：FTS5 + 向量 + RRF     ← 给智能体查
抽取层   PDF/Office/OCR → 正文         ← CPU 密集
切块向量层 chunk → embedding → .npy     ← GPU 密集
事实源   原文件（原位只读，绝不搬动）
─────────────────────────────────────
算力层（横切） 控制台 / 生产主机 / 算力节点
```

> **🤖 给智能体：这份文件是写给你照着做的工作手册，不是给人看的说明书。**
> 读完这一节就往下走，按「三、七步流程」→「四、抽取→切块→向量」→「十四、怎么跑起来」的顺序，
> 一步一步执行；每一步的输出文件都写到指定位置，跑完再进下一步。
> 遇到「五、调优」和「十一、踩坑」时先扫一遍，能省掉大部分返工。
> 文中所有 `<盘符>` `<输出目录>` 由你按实际环境替换。

**索引放 SSD，语料放 HDD——这条比选什么框架更重要。** FTS5 随机读密集，机械盘上每次查询等磁头寻道，
固态盘直接命中页缓存。语料几 TB 便宜地放着，索引几百 MB 放在贵的地方。
别因为"盘大"就把索引放过——最常见的一次性错误。

> **Obsidian 和 LLM Wiki 只是展示层，真正的价值在检索层**——Office 点不开就只剩文件名。

**规模实测**：2 千到 3.7 万文件跑同一套流程，最大一档 37,782 个 / 27.7 GB → 2,066 个 / 10.7 GB。

## 三、七步流程（只读在前，动手在后）

**第 1 步 全量探针（只读）**：清单（路径/名/大小/mtime/扩展名）；只读首尾 64 字节判魔数，不解析正文；
四类分诊——正常/格式伪装/损坏/加密占用。不摸家底就动手后面全是返工。典型：201 个 `.doc` 实际是 HTML；
7,122 个 NAS 同步损坏无文本层；6 个 PDF 是"权限加密"，空密码就能开。

**第 2 步 SHA-256 去重（只读）**：只对"正常"文件算哈希；完全重复合并成组、留一个代表；版本族只聚类不判最新。
**精确重复只认 SHA-256**——同名不代表同意，同大小也不代表同意。实测某目录 291 个重复组、719 个文件，省 3.89 GB。

**第 3 步 分层抽样试读（只读）**：按"目录 × 年代 × 大小"抽 400-500 个；旧 `.doc` 先魔数嗅探挑假 doc
再试跑 100 个；试读前后全量重算 SHA 必须 0 变化。**关键是"证明自己没改文件"**。

**第 4 步 自动分诊三堆（只标注）**：A 有用 / B 垃圾 / C 待定。**C 堆必须按"文件族"聚合**——
几万个待定列成行没人看得下去，聚成几十族才行。典型 B 堆：`~$` 锁文件、`.DS_Store`、
0 字节空文件、下载失败的占位、十六字节临时脚本。

**第 5 步 批量裁决（只标注）**：套 28 条规则，每族给终态 `keep / keep_index / delete / needs_review`。
核心：D01 同名多版本→留日期最新、其余只留索引；D21 旧版/备份/副本→人审；
D26 精确重复→只认 SHA-256；D27 归属不明→人审。

**第 6 步 建实体卡**：五类实体（项目/方案/机会/规范/采购），十五个 YAML 字段 + 九段正文。铁律两条：

- **证据分级不能抬**：`strong`（有中标公告/成交通知书/合同）、`directory-only`（只有目录名）、
  `unknown`（推断）。"待核"只能用于事实判断（客户是谁、多少钱），不能用于证据等级。
- **金额口径写死**：「本金额为 XX（预算/限价/报价/成交/合同），不可与其他数字相加」或「未采信任何金额」。
  不做口径标注，后续一定被跨卡相加，得出错误总数。

**第 7 步 呈现层（可选，给人看）**：`index.md` + 属性视图 + 主题页 + 决策页 + 问答页。
**只给人看**，智能体用检索层就够了。

## 四、抽取 → 切块 → 向量：三步都不能省

**抽取**（从原始文件里把正文抓出来）：文本层能读就读，扫描件走 OCR，加密就跳过，输出每份文档一行。
**这步 100% 吃 CPU**——实测 24 核跑满、GPU 0%、温度不动：文本解析是 I/O + 字符串，无矩阵运算。

**切块**（把长文按字数切成小块便于召回）：400 字一块、重叠 50 字。既不让一块太长（语义稀释），
又不让上下文断掉（重叠兜住边界）。策略必须固定并记录版本，块数和 `chunk_id` 严格 1:1，
否则向量和正文对不上、检索全错位。

**向量化**：512 维、float16。GTX 1060 6 GB → RTX 4060 8 GB 快 4-6 倍，
**embedding 是流水线里 GPU 收益最大的环节**。指纹固定：模型名 + revision + 维度 + 归一化方式。

**融合**：FTS5 出 N 条（按 bm25）、向量出 N 条（按余弦），RRF 按名次投票出 top_k。
顺序不能换：先有块才能向量化，先有向量才能融合。

## 五、昨天到今天的调优全过程（2026-10-27 ~ 10-28）

### 5.1 怎么发现的：库里有，模型说没有

用户问一个东西，明明录进过库，模型答"没找到相关材料"，但直接怼数据库 FTS5，10 条精准命中。
**不是没数据，是被埋了。**

### 5.2 根因一：FTS5 默认 trigram 分词，中文两字词全废

FTS5 用 `tokenize='trigram'`（按 3 字符滑窗建索引）。英文还凑合，中文彻底崩：
**11 个两字词查询，11 个全 0 命中**——"合同""预算"根本凑不出完整三元组。改法：
**jieba 切词 + `tokenize='unicode61'`**，入库前先分词再压空格喂给 FTS5。
**教训：中文语料上分词策略比索引结构重要一个数量级，默认值默认不适合你。**

### 5.3 根因二：一份 xlsx 顶 130 份 PDF，任何查询都挤进候选池

库里有份超大 Excel，抽出正文切出 **5 万块**；全库平均每份文档只有 **365 字/块**，这一份顶 130 份 PDF。
不管问什么，这份表的块都在候选池里，把该出现的文档挤到后面。
**不是检索算法错了，是候选池被一份文档垄断了**——这是"检索污染"不是"检索不准"，
修的方向不是调分，是**让大文档别霸榜**。

### 5.4 修复五项（全部通用，不针对任何具体项目）

```
① 文档块数降权   factor = (500/n)^0.5，n 为该文档块数；n > 5000 时 ^0.8（罚更狠）
                 块越多每块乘的系数越小，5 万块那份被压到原来的十几分之一
② 表格密度降权   制表符/竖线/数字占比 > 60% → ×0.5
                 表格抽出全是数字和分隔符，按字面极易命中，但对自然语言问句没信息量
③ 每文档上限 20  一份文档最多贡献 20 个候选块，堵死"单文档多数派"，比 ① 更直接
④ 目录路径证据   匹配完整相对路径 + 最少覆盖率门槛（路径得真覆盖到关键词，不能沾边就算）
                 不建文书类型词表——一建就得维护、换项目就失效；问"哪个方案"时目录名比正文可信
⑤ 词项 60 压到 12  查询只取前 12 个高信息量词项。这是变快的原因——候选集小了，
                 向量检索和 RRF 排序都跟着省
```

### 5.5 修前后对比

| 指标 | 修前 | 修后 |
|---|---|---|
| 查询延迟 | 96–203 ms | **24–96 ms**（反快） |
| 三组原先答不上的问题 | 全部失败 | **全部命中正确文档** |

**延迟反而降了**——候选池从几千条缩到几百条，省下的计算远超降权逻辑开销。

### 5.6 心法与调优纪律

> **不是"让对的答案分数更高"，而是"让错的答案没机会进候选池"。**

```
① 改前记录语义查询排序（基准）→ ② 改后再跑一遍逐条对比 → ③ 确认"没退化"才算成功
④ 性能一律串行测（并发会争用模型锁，测出 211 ms 误判超时）
```

另一条老经验仍有效：不是所有查询都该一把抓。含扩展名、型号、日期、工单号、大写缩写且词数 ≤ 3
判"文件意图"，正文/向量各只取 20 条；含"如何/怎么/原理/配置/故障/方案"的一律判语义查询。
**正文和向量的权重一点没动——这是语义查询不退化的前提。**

## 六、在线 vs 离线模型横向对比

同一条检索链路换两种模型作答。**趋势结论，不是跑分表。** 在线 DeepSeek API（`deepseek-chat`）；
离线本地 Ollama `qwen3.5:9b`，RTX 4060 Laptop 8 GB，**全程拔网线（完全断网）**。

**速度**：云端 0.7–1.1 s、稳；本地 9B 0.9–4.1 s、抖动大。云端快约 **2–2.5 倍**，
本地忽高忽低跟显存占用和思维链长度有关。

**质量**：**理解、总结、读方案基本打平**——材料给够，9B 表现比预期好。但本地小模型有两个硬伤：

- **多位数乘法会算错**——折扣率、单价 × 数量这类题经常算错，而且错得很自信。
- **表格被抽成一行后会把状态张冠李戴**——每行挤成一串，模型会猜哪一行的"无""已过期"
  对应哪个对象，猜错概率很高。

**信息不足时差异很大**：云端更倾向说"不确定/材料里没有"，本地小模型更倾向**脑补**。
知识库场景里，**会说"没有"比"编一个"重要得多**。

**成本**：云端每次几分钱，本地**零成本**（只有电费）。但成本不是主要矛盾——见下条。

**关键发现：瓶颈在检索层，不在模型层。** 检索没给对材料的题两边都答不出来，
换更大的模型也没用——变不出没进候选池的文档。

```
⇒ 优化方向是召回质量（切词、降权、候选上限、路径通道），不是换更大模型
⇒ 换了模型还答不上的题，先去看检索日志里到底召回了什么
```

这条直接决定了 5.4 那五项修法的优先级。**选型建议**：读内容 / 写总结 / 完全离线 → 本地 9B
（够用且不出网）；算钱 / 对表格 / 判合规状态 → 云端 API（会承认不确定，算术不出错）。

**一个实操坑：thinking 把答案吃光。** `qwen3.5` 系列**默认开 thinking**，思维链把
`num_predict` 吃满，`answer` 字段**是空的**。必须显式传：

```json
{"model": "qwen3.5:9b", "think": false, "options": {"num_predict": 1024}}
```

| 同一题 | 耗时 | 答案 |
|---|---|---|
| 开 thinking | 20–52 s | 0 字 |
| 关 thinking | 1.6–3.1 s | 直接出答案 |

**排查提示**：本地模型"答空了"或"特别慢"，先看 thinking 关没关。

## 七、Everything 作为"找文件"的第一层

> **前提：Windows + NTFS 方案。Linux/macOS 不是这套，那边用 `grep` / `find` / shell 脚本。**
> 已独立发布为技能 `everything-http-search`，本仓库有副本。

### 7.1 为什么不点 UI

因为要**能被 agent 调用**——走 HTTP API（`http://127.0.0.1:8089`），一行 curl 就能查。

**核心价值：读 NTFS 的 MFT（主文件表），秒级索引、零 Token、变动自增量（USN 日志）。**
几十万文件查一个名字是毫秒级——**80% 的"找文件"场景根本不需要向量化。** 顺序排在检索之前：

```
问"有没有 X 这个文件"    → Everything（毫秒、零成本）
问"X 这个方案讲了什么"    → 知识库检索（切块 + 向量）
```

### 7.2 装一次，开机就能查（别每次手动启）

**关键认知：agent 不该依赖"人先手工点开 Everything"。** 开机自启 + 静默托盘 + HTTP 常开，这三件事一起配好，之后 `curl http://127.0.0.1:8089` 随叫随到。

#### 三行 ini（先关程序，改完再启）

```ini
http_server_enabled=1
http_server_port=8089
http_server_bindings=127.0.0.1    # 只本机；跨机才改 0.0.0.0
show_tray_icon=1                  # 原来 0 时关了窗口就找不回来
minimize_to_tray=1                # 点 × 缩托盘，不退出
minimized=1                       # 启动即最小化
```

#### 启动文件夹放快捷方式（带 `-minimized`）

```powershell
$exe = "C:\Program Files\Everything\Everything.exe"
$lnk = "$env:APPDATA\Microsoft\Windows\Start Menu\Programs\Startup\Everything.lnk"
$ws  = New-Object -ComObject WScript.Shell
$s   = $ws.CreateShortcut($lnk)
$s.TargetPath = $exe; $s.WorkingDirectory = Split-Path $exe
$s.Arguments = "-startup -minimized"; $s.WindowStyle = 7
$s.Save()
```

#### 重启后这样验

```powershell
Get-Process Everything                              # 有进程
Get-NetTCPConnection -LocalPort 8089 -State Listen  # 1 条
(Get-Process Everything).MainWindowHandle           # 0 = 无窗口（真静默）
```

**实测**：重启 1.4 分钟全部就绪，无任何弹窗，8089 立即可查。

#### SSH 里临时拉起（只在被误退出时用）

普通 `Start-Process` 起的进程会被 SSH 断连带走，必须投交互会话：

```bat
schtasks /create /tn "Everything-HTTP" /tr "C:\Program Files\Everything\Everything.exe -startup -minimized" ^
  /sc once /st 00:00 /it /f
schtasks /run /tn "Everything-HTTP"
```

`/it` 是关键——只有投到交互会话，UI 和 HTTP 服务才起得来。但**它不适合当开机自启**，开机自启用启动文件夹。

> **托盘类配置的坑**：从 SSH 启的进程在隔离 session 里建不出托盘图标，设了 `minimize_to_tray=1` 会直接退出，日志 `tray icon error: os error -2147467259`（E_FAIL）。改完这类配置让用户自己点图标启动。

### 7.3 三条铁律

**① 不加盘符 = 搜全部已索引的盘**。别自己缩范围——你以为"肯定在某块盘"，它偏在外接硬盘里。

**② 正则作用于"完整路径 + 文件名"**，加路径限定必须写 `regex:.*xxx` 而非 `regex:xxx`：

```python
"regex:方案.*\\.docx"      # 错：只匹配路径开头
"regex:.*方案.*\\.docx"    # 对：路径任意位置
```

**③ 问"我有哪些 X"必须先搜目录**。只搜文件名会漏掉整个主题文件夹——
文件夹叫"XX 项目资料"，里面 200 个文件名都不带"XX"。

## 八、降噪规则

**一律删除，无需人审**：`iso img vhd vhdx ova ovf vmdk qcow2`（虚拟化镜像）、`exe msi msix appx`（Win 包）、
`deb rpm pkg dmg`（Linux/macOS 包）、`apk ipa`（移动端）、`so dll sys ocx a lib`（库/驱动）。
例外保留：业务 APP 的 apk、便携工具、项目配置盘（`.vdi`）。

**系统垃圾**：`~$` 开头的 Office 锁文件、`.~` 临时占位、`.DS_Store` / `._` 开头的 macOS 残留、
`.download` 结尾的下载失败文件、0 字节空文件（先确认是否补件）。

**特殊标注必须保留**（最易误删——名字像版本，实际是不同业务对象）：
`（内部）/（客户侧）`不同受众、`（模板）/（OCR）`不同类型、`附件1/附件2`不同附件、
`优化服务/运维服务/运维及优化服务`不同业务——**都留**。

**按月资料不是版本**：月报、月度统计文件名只差日期 → 整族保护，不参与版本比较。

**扫描件不能一刀切**：有文本层→正常抽取；无文本 + 命中「中标/成交/合同/通知书/结果」→ 渲染关键页；
无文本 + 不命中→`directory-only`。中标/成交通知书常是扫描件，一刀切会把 strong 证据降成目录依据。

**大目录（500+ 实体）分层建卡**：`score = 文件数 + 3 × 证据数`，TOP 30% 建主卡（`card_tier: main`），
后 70% 只写总索引一行，已有卡标 `archive`，不推倒重来。**金额不进公式**——藏在正文里覆盖不全。

## 九、数据边界：什么出网，什么不出网

准确口径：**数据不整体外流，但查询时命中的片段和问题会出网。**

```
✅ 不出网：原始语料（33 GB）、40 万个块、950 MB SQLite 索引、412 MB 向量
          ⇒ 全部在三台机器硬盘上，一份没传出去
⚠️ 会出网：查询时被选中的 top-k 片段（10-50 个块）+ 用户提的问题
          ⇒ 送云端模型做理解和组织，出去的是"片段"不是整份文档
```

原始文件、抽取切块、FTS5 索引（本地硬盘/CPU/SSD）、向量计算、查询编码、检索、RRF（本地 GPU/内存）
——**全部 ❌ 不出网**；只有**命中片段 + 问题 → 生成答案**走云端，**✅ 出网**。

三个必须说清的判断：

**① 不是"零出网"，是"不整体外流"**——存储检索本地，但语义理解在云端。

**② 风险落点**：查技术手册无所谓；查客户名单、报价、合同条款，那几段确实出网了——
敏感语料要不要进库得先判断，别先建库再想。

**③ 要彻底不出网，唯一的路是本地模型**（7B 量化 6-8 GB 显存、32B 要 24 GB；慢 5-10 倍、
中文弱一档）。现接了 9B，对比见第六章。

## 十、让 Obsidian 能点开原件

不做这一步，知识库就只有文件名，什么都点不开。Markdown 只能链 `.md`，链不到 doc/pdf/xls，
解法是 `file:///` 外链。

**关键：链接必须写在正文，不能写在 YAML**——frontmatter 里的 Markdown 永远不渲染，只显示原始字符串。

```markdown
### 来源链接
| 标记 | doc_id | 文件 | SHA-256 |
|---|---|---|---|
| 主体 | SRC-xxxxxxxx | 📕 [某某中标通知书.pdf](file:///<盘符>/<URL编码路径>) | xxxx… |
```

**路径必须 URL 编码**（中文、空格、`(` `)`），`(` `)` 不编码会直接打断 Markdown 链接语法：

```python
from urllib.parse import quote
uri = "file://" + quote(path.replace("\\", "/"), safe="/:")
```

**验证三点**：① 切阅读视图（Ctrl+E）才看得到蓝色链接；② 路径全 `os.path.exists` 过一遍；
③ 链接数 = 来源数。**建卡时就写进 sources**，否则后期加不了链接。

安装：装到用户目录，首次启动选"打开本地文件夹作为 vault"；设置→通用→命令行界面启用 CLI；
设置→文件与链接→外部链接→用默认程序打开。CLI 常用
`obsidian vault=<名> files total` / `read file=<笔记名>` / `backlinks … total`。
**中文输出会乱码**：落文件 + `chcp 65001` + base64 回传。

## 十一、踩过的坑（一条都不删）

**这是最有价值的部分，一条都别跳过。**

| 坑 | 现象 | 解法 |
|---|---|---|
| 解析器写回元数据 | 读 `.xls` 后 SHA 变 | 复制到临时目录再读，或用 xlrd/pandas |
| 双链正则误报断链 | 报 59% 断链实际 0 | 非贪婪 `+?` + 单独吃 `\\?`，只比文件名 |
| CLI 不认未注册 vault | `Vault not found` | 改 obsidian.json 加 key + 重启 |
| 链接写在 YAML | 永不渲染 | 挪到正文表格 |
| 中文没 URL 编码 | 链接断 | `quote(path, safe="/:")` |
| 打开备份目录验证 | 像没改成功 | 确认路径是真正的 vault |
| 源码视图 | 链接不渲染 | Ctrl+E 切阅读视图 |
| 只读属性挡删除 | WinError 5 | `os.chmod(path, stat.S_IWRITE)` |
| 唤醒进程随 SSH 断连被杀 | 输出文件不存在 | `schtasks /create /sc once /it` + `/run` |
| 按月资料被当版本删 | 29 个月报只留 1 个 | 整族保护 |
| 索引放机械盘 | 热查询几百毫秒抖动 | 挪固态盘，稳定 100 ms 级 |
| 各通道取一样多候选 | 正文淹没文件候选 | 短查询词收窄正文候选 |
| 并发测延迟 | 争用模型锁，测出 211 ms | 性能数据一律串行跑 |
| 型号分隔符不一致 | 写 `<型号>` 文件叫 `<型号>` 匹配不上 | 忽略 `- _ .` 空格 |
| 裸扩展名查询 | 查"ISO"返回 `iso2022jp.go` | 裸扩展名优先按扩展名过滤 |
| 同一文件在两个库 | 占掉两个推荐位次 | 文件意图只取文件目录库 |
| embedding 换模型不重建 | 向量正文错位，检索全错 | 换模型 = 全量重建 |
| FTS5 用默认 trigram | 中文两字词 11 测 11 全 0 | jieba 切词 + `unicode61` |
| 单份大表 5 万块 | 任何查询都挤进候选池 | 块数降权 + 每文档上限 20 |
| qwen3.5 默认开 thinking | 答案 0 字、耗时 20-52 s | 显式传 `"think": false` |

## 十二、老 Office 格式：LibreOffice 无头模式

**先说结论：当前脚本对这 8 个扩展名根本不尝试解析。不是"慢"，是"没做"。**

```python
UNPARSED_EXTENSIONS = {".doc", ".xls", ".ppt", ".wps", ".rtf", ".zip", ".rar", ".7z"}
```

仍进清单、保留名/路径/大小，但提取阶段跳过，正文不进 FTS5、不生成向量——**只查得到文件名，查不到内容**。

> **走过但弃用的路线：调 Office 程序来转换。** 实测弃用：**会丢超链接、会静默失败、受 Office 版本影响**
> （没装就报错，装了也可能被兼容提示卡住），且会写回元数据让 SHA 变。
> 复制到临时目录能保住原文件，但消不掉启动开销和无人值守时的弹窗风险——**作为批量方案代价太大。**

对 Word 类文件改用 **LibreOffice 无头模式**：
`soffice --headless --convert-to docx --outdir <输出目录> <文件>`。
成功后交给正常 `python-docx` 流程。`.xls`/`.ppt` 各自转 OOXML；压缩包先解包再递归。
**不要把 8 个扩展名不加区分地都转成 docx。**

优点：不依赖 Office、跨平台、只读原文件另写新文件、无弹窗。缺点：装 LibreOffice 约 700 MB；
一次只转一个要自己循环；老复杂排版（表格、文本框、艺术字）可能丢内容或变结构——
**产出是"近似还原"，不是 100% 一致。**

**先小样本再决定是否全量**：按扩展名/年代/大小分层抽样，输出到临时目录逐项验证——
① 转换前后原文件 SHA-256 必须 0 变化；② 记录成功率、失败原因、单份耗时；
③ 抽查正文、表格、页眉页脚、文本框；④ 用已知关键词跑 FTS5 确认正文真进了检索。
可接受再分批扩大；失败率过高就停下，继续标「仅登记、未解析正文」。
**不能把"转换命令跑完"写成"内容已完整索引"。**

## 十三、三台机器实践记录

**为什么不用一台机器**：生产主机开着挂查询服务、不开机能省电；算力节点批量计算时 24 核全满，
会拖死同机服务。**关键不是"谁常开"，而是"谁随时能接管"。**

| 角色 | CPU | 内存 | GPU | 存储 | 状态 |
|---|---|---|---|---|---|
| 生产主机 | 6 核 12 线程 | 32 GB | GTX 1060 6 GB | SSD 465 GB（索引）+ HDD 1.8 TB | 按需开机 |
| 算力节点 | 24 核 32 线程 | 32 GB DDR5 | RTX 4060 8 GB | NVMe 1 TB | 插电 + 网线才上岗 |
| 控制台 | 4 核 | 8 GB | 无 | 小容量 | 常开 |

生产主机不必 7×24：不用就关，服务用时再起，冷启动约 1.1 秒，模型常驻后热查询 60-90 ms。
**真正要 7×24 的只有一样：数据不能丢。可靠的是资产，不是机器。**

**CPU 满载 vs GPU 上岗**（被监控数据逼出来的认知）：抽取 24 核全满、GPU 0%、温度不动（文本解析无矩阵运算）；
切块 CPU 中等；**向量化 CPU 低、GPU 满载**；建库 FTS5 短暂满载。流水线：CPU 满载几小时 → 空档 →
GPU 满载几十分钟 → CPU 再上几十秒。所以向量化从生产主机搬到算力节点，6 GB → 8 GB 快 4-6 倍，
**值得单独调度一台机器**。

**两条路并行**：路 1 本地 RAG；路 2 整段任务交给算力节点（数据过去、算完、回来）。
本质是"按需租用算力"，只不过租的是自己桌上那台——大厂用加速卡/光纤，我们用笔记本+千兆网线。

**通信**：控制台→节点走 ACP 信箱 + SSH 唤醒；节点间走千兆网线或快照；查询走 HTTP 常驻。
铁律：**传「需求」不传「动作」**——不 scp 塞文件、不远程执行二进制，写需求单 → 对端 agent 读 →
自己做 → 自己回执。说"要什么"比"怎么做"可靠。

**会留下的文件**：`manifest.json`/`files_ruled.csv`/`dedupe_report.json`（清单/裁决/去重）→
`documents.jsonl`/`chunks.jsonl`/`chunk_ids.json`（文档/块/ID 对齐）→ `vectors.f16.npy`/`vector_meta.json`
（N×512/指纹）→ `kb.sqlite3`/`catalog.sqlite3` → `INDEX_COMPLETE.json`/`acceptance_verify.json`
/`benchmark_results.json`/`status.json`（标记/校验/基准/exit_code）。每阶段留 **输入数、输出数、耗时**。

没有这三个数等于没跑过，出问题分不清"没读到"还是"读了没写"。**「跑完了」不是结论，「校验通过」才是。**

**性能参考**（60 次串行）：冷启动 1,121 ms；服务端 P50 61 / P95 72 ms；端到端 P95 91 ms
（P50/P95 把耗时排队取第 50/95 名，比平均值更能反映"偶尔卡一下"）。最贵的是向量检索
（约 45 ms，55 万条精确余弦），FTS5 约 7 ms，RRF 约 2 ms。**这规模下暴力搜索够用，不需要向量数据库。**

**这次没做但该做的**：重排（rerank）、增量索引（现全量重建）、权限隔离、对象存储、卡片自动提炼
——每条都是下一步的入口，不是缺陷。

## 十四、怎么跑起来

表结构见 [references/schema.md](references/schema.md)，模型见 [models.md](references/models.md)。

```bash
pip install -r requirements.txt        # OCR 再装 rapidocr-onnxruntime

python scripts/build_full.py   --source-dir <语料根> --output-dir <主库输出>
python scripts/build_index.py  --output-dir <主库输出>
python scripts/build_others.py --source-dir <第二库语料根> --run-root <中间目录> --output-root <第二库输出>
python scripts/build_catalog.py --source-dir <目录一> --source-dir <目录二> --output-dir <目录库输出> \
  --privacy-dir-name <需整树排除的目录名>
python scripts/query.py --query "<问题>" --main-dir <主库输出> --others-dir <第二库输出>
python scripts/verify.py --output-dir <主库输出>    # 验收校验单独跑
```

默认模型 `BAAI/bge-small-zh-v1.5`（512 维、float16），从 HF 缓存加载，或 `--model-dir` 指定离线路径。

| 算力 | `--batch-size` | 预期 |
|---|---:|---|
| 8 GB 显存 | 32 | 全量向量化约 30-60 分钟 |
| 6 GB 显存 | 16 | 约 2-3 小时 |
| 4 GB 或更少 / 纯 CPU | 8 | 慢 4-6 倍，先用小样本验证 |
| 内存低于 16 GB | 8 | 抽取分片跑，别一次扫全部 |

向量化用 `--batch-size`、抽取线程数用 `--workers`。**路径全是参数、没有默认值——换机器只改参数。**

## 十五、给智能体的用法

1. 先读本文档　2. 按七步走，每步产出落文件　3. 每步给数字（文件数/大小/分诊结果）
4. 判不了的进 C 堆 / `needs_review`，不许硬猜　5. 删除等用户点头，标注不删除

查询侧：精确问题（型号/编号/金额/日期）走文件意图、FTS5 主导；模糊问题（怎么办/类似的有哪些）
走向量语义；两路出候选、RRF 融合。要摘要看卡片，要看原文点 `file:///` 链接。
**问"有没有这个文件"先走 Everything（第七章），别一上来就向量化。**

## 十六、一句话总结

> **方法论在七步，重头在证据层。**
> **FTS5 查字面，向量查语义，RRF 投票——两条腿缺一条就瘸。**
> **修的不是分数，是候选池：让错的答案没机会进来。**
> **瓶颈在检索层不在模型层——换更大的模型救不了召回。**
> **索引放 SSD，语料放机械盘，这个分离比选什么框架更重要。**
> **Obsidian 只是展示层，别喧宾夺主。**
